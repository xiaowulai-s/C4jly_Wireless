## 二、两类损坏机制（务必区分）

### 类型 A：GBK 字节被按 UTF-8 解码
原始 GBK → 按 UTF-8 解码（非法字节替换为 `U+FFFD`）→ 存为 UTF-8。
特征：文件是**合法 UTF-8**，含 `EF BF BD`；Read/Grep 显示 `��`。

### 类型 B：`锟斤拷`
`U+FFFD` 再编码为 UTF-8（`EF BF BD`）后又被按 GBK 解读。
特征：文件是 **GBK**，但含 `EF BF BD` 字节；**在 Keil 里就是可见乱码**，且字符级不可逆。

> **第一轮扫描为什么漏掉类型 B**：`EF BF BD` 在 GBK 下是合法汉字（`锟斤拷`），既不产生 `U+FFFD` 也不报编码错误。**双线索扫描（`EF BF BD` 字节数 + `U+FFFD` 数）必不可少。**

## 四、核心方法（可复用）

### 1. 损坏函数 oracle —— 把"猜测"变成"可证明"
- 类型 A：`corrupt(t) = t.encode('gbk').decode('utf-8','replace')`
- 类型 B：`corrupt2(t) = corrupt(t).encode('utf-8').decode('gbk','replace')`

两者都是**确定性函数**。任何候选原文都可以「再损坏一次」与观测到的损坏字节逐字节比对——**完全一致即为数学证明**。本轮 168 行由此证明；对无法证明的行，则按语义重建。

### 2. 干净源定位（git 是关键）
- `cc6bb0a`（2026-09-04 提交）对 4 个类型 B 文件**全部干净**（`EF BF BD=0`）
- `HEAD:...main.c.bak` 为 `main.c` 专用干净源（579 行）
- 类型 A 的干净源在 `d5e042d`
- 另发现 `.rev2.bak` / `.bak` 等已删除备份可用 `git cat-file blob HEAD:<path>` 恢复

### 3. 自动还原必须用 oracle 复核
对齐旧干净源会**回退后来改过的注释**。本轮纠正了 4 处：
- `battery.c` L15/L67 原文是「**电压**\*分压比」（旧源写成"电池"）
- `sensor.c` L2 原文含「便携式」、L4 是「功能概述」、L107 是「全局中断」

### 4. 三重安全校验
1. **注释外代码流零改动**（注释剥离器逐字节比对）
2. **行尾符逐行继承**原文件（本项目源文件是混合行尾，如 `sensor.h` 74×CRLF + 1×LF）
3. **注释内保留原有 ASCII 结构**，重建时先看 `ASCII骨架` 再落笔

## 五、注意事项（写给后续维护者）

1. **禁止用会输出 UTF-8 的工具（Write/Edit 等）直接改写含中文源文件**——必须先写 UTF-8 临时文件，再「UTF-8 读入、GBK 写出」转回。
2. PowerShell 读写这些文件必须用 `[System.Text.Encoding]::GetEncoding(936)`；**PS 5.1 的 `-Encoding gbk` 无效**。
3. **改写前先判定单文件实际编码**（本项目曾是混合态）。
4. **扫描乱码必须双线索**：`EF BF BD` 字节数 + `U+FFFD` 数。
5. 编码二次毒化**不可逆**：本轮 227 行原文已永久丢失，只能语义重建（注释文案与原文措辞可能有差异）。
