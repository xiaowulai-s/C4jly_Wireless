## 一、P0-A（✅ **v53 已修 · 真机通过**）：USART3 缺 `HAL_UART_ErrorCallback`，一次 ORE 即永久失联

**位置**：`Core/Src/main.c:194-210` + `HAL_UART_Receive_IT` 全部调用点

```c
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart) {
  if (huart != NULL && huart->Instance != USART3) return;
  { int gr = hmi_get_feed(rx_byte); ... }
  HAL_UART_Receive_IT(huart, &rx_byte, 1);   /* ← 唯一的重挂路径, 只在正常回调里 */
}
```

**已核实的事实**（grep 全工程确认）：
- `HAL_UART_ErrorCallback` **在本工程完全未实现**（只有 HAL 库的 `__weak` 空版本）
- `HAL_UART_Receive_IT` 全工程**只有 2 处**调用：`main.c:209`（RxCplt 回调内）与 `main.c:375`（初始化）

**机理**：单字节 `Receive_IT` 模式下，若屏端 UART 因电磁干扰 / 屏重启脏数据 / 热插拔收到噪声字节，
第二个字节在处理第一个的窗口内到达 ⇒ **ORE（Overrun）**。
STM32 HAL 把 ORE 归为 blocking error，会调 `UART_EndRxTransfer()` 清掉 `CR1.RXNEIE` 并把 `RxState` 置 READY，
**而错误分支只调 `HAL_UART_ErrorCallback`（本工程没实现）⇒ `RxCpltCallback` 永远不会被调用 ⇒ `Receive_IT` 永不重挂。**

**后果**：屏幕接收**永久失效** —— 触摸无响应、屏发什么都不响应，**且无法自愈**（除复位外无任何恢复路径）。
现场表现就是「屏突然失灵，重启才好」。

**修法**：实现 `HAL_UART_ErrorCallback`，对 USART3 做「清错误标志 + 重新 `Receive_IT`」：
```c
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart) {
  if (huart == NULL || huart->Instance != USART3) return;
  __HAL_UART_CLEAR_OREFLAG(huart);          /* 清 ORE(必须先读 SR 再读 DR) */
  HAL_UART_Receive_IT(huart, &rx_byte, 1);  /* 恢复接收 */
  /* 顺带: hmi_get_feed 的帧状态机若有残留, 应 hmi_get_reset() */
}
```
★ 建议同时在 `hmi_get_reset()` 处加一处调用，避免错误后残留半帧。

## 一之二、P0-B（✅ **v53 已修 · 真机通过**）：HardFault 是死循环，且**软件看门狗救不了它**

**位置**：`Core/Src/stm32f1xx_it.c` 的 `HardFault_Handler` + `Core/Inc/stm32f1xx_hal_conf.h:52`

```c
void HardFault_Handler(void) { while (1) { } }     /* 死循环, 无任何恢复 */
/* hal_conf.h:52 */  /*#define HAL_IWDG_MODULE_ENABLED */   ← 硬件 IWDG 未启用 */
```

**已核实**：`.uvprojx` 全工程无 `stm32f1xx_hal_iwdg.c`，`iwdg` 零命中 ⇒ **硬件独立看门狗确实未启用**。

**后果链**：任何 HardFault（野指针 / 非法栈 / 除零）⇒ 主循环停 ⇒ `iwdg_feed()`（`main.c:265-268`，软件模拟，阈值 4 s）**永不再执行** ⇒ `NVIC_SystemReset()` 永不触发 ⇒ **设备永久死机，屏无任何提示**。

这正是硬件 IWDG 的标准用途。**真实产线设备缺此保护 ⇒ 一次偶发异常即报废，需返厂。**

**修法（两条路）**：
- **短期（软件兜底）**：HardFault / Error_Handler 里改调`NVIC_SystemReset()`（死循环换成复位），配合错误计数器防止"复位风暴"
- **正解（硬件）**：启用 IWDG（`stm32f1xx_hal_iwdg.c` 加入工程 + `HAL_IWDG_MODULE_ENABLED` + LSI 时基 + 喂狗点已存在），窗口设 4~8 s

★ 注意：`Error_Handler`（`main.c`）也是 `__disable_irq(); while(1){}`，同样死锁。

## 二、P1-A（✅ **v56 已修**）：校时期间用户的阈值按键可能被丢弃（★ 机理已在 v56 订正，见下）

**位置**：`Core/Src/main.c:893-902`（`thr_hi_readback_poll`）

```c
if (g_rtc_wait) return;   /* [v51] RTC 占用通道 -> 本轮不发 */
if (g_thr_try >= 5u) { g_thr_hi_req = 0; g_thr_try = 0; g_get_busy = 0; return; }  /* 放弃 */
```

**时序推演**（校时需8 步：1 次秒值活性探测 + 6 项 + 可能重读）：

| 时刻 | 事件 |
|---|---|
| t0 | RTC 发 get，`g_rtc_wait=1`，deadline = t0+500 |
| t0+250 | 用户按阈值键盘 → `g_thr_hi_req=1`；`thr_hi_readback_poll` 见 `g_rtc_wait` 让出 |
| t0+500 | RTC 本步超时 → `g_rtc_wait=0`；同轮 `thr_hi_readback_poll` 抢占 → `g_thr_try=1`，发 get，`g_get_busy=1` |
| t0+750 | RTC 想发 → `g_get_busy=1` → 让出 |
| … | 每轮都被抢，`g_thr_try` 累到 5 ⇒ **`g_thr_hi_req=0`（用户这次按键被丢弃！）** |

**影响**：用户在上电后几秒内（正是校时窗口）按高报阈值，**可能按了没反应**。
下一次按键会重新尝试（`g_thr_try` 已清 0），所以不是永久失效。

**与v51 原目标的关系**：v51 修的是「RTC 读数被误当阈值**落盘**」（危害更大）；
本条是「阈值按键偶尔不生效」（危害较小，但确实是 v51 引入的副作用）。

**修法（推荐）**：把阈值让出**只做一次**，而不是连续 5 次让出——
```c
if (g_rtc_wait) { g_thr_wait = 0; g_get_busy = 0; g_thr_try = 0; return; }  /* 等下一轮校时步过去 */
```
或：把校时优先级降低（校时让阈值），因为校时会自动重试、而用户按键不会。


### ★★ 机理订正（v56 实施时发现，本节原描述有误）

**原文写的是「互斥让阈值连续让出 5 次后 `g_thr_hi_req=0` 丢弃该次按键」—— 这个机理是错的。**

v55 实际代码：

```c
static void thr_hi_readback_poll(void) {                        /* v55 */
  if (g_thr_wait) { if (now > g_thr_deadline) { g_thr_wait = 0; g_get_busy = 0; } else return; }
  if (g_rtc_wait) return;               /* ← 让出, 在下一行之前 */
  if (g_thr_try >= 5u) { g_thr_hi_req = 0; ... return; }         /* ← 放弃 */
  g_thr_try++;                                    /* ← 计数只在这一行 +1 */
```

`if (g_rtc_wait) return;` 在 `g_thr_try++` **之前** ⇒ **让出通道根本不消耗重试预算**。
真正吃掉 5 次预算的是**每次 `tjc_get()` 的 500 ms 应答窗口到期**。

**真正的丢失条件 = 500 ms 窗口 < 上电阶段屏重建页面的阻塞时长**（`refill_table()` 一次约 1.8 s），
⇒ 上电后那几秒内按阈值，5 次全超时 → 按键被静默丢弃，与实测现象吻合。

**v56 改法**：放弃判据由「重试 5 次」改为「墙钟 `THR_HI_PATIENCE_MS = 8000u` 未获应答」——
屏幕慢不再被误判为「不响应」，只有连等 8 s 才放弃（那才是真故障）。
`g_get_busy` 的清除**仍然必须保留**（漏了会让 RTC 校时永久堵死）。

**残留风险已核对**：放弃边界上迟到的回包会被 RTC 分支消费，但阈值 `100~1500` 与年份 `2020~2099`
不重叠 ⇒ 被 `y >= 2020` 校验拒绝 ⇒ RTC 自动重试，**自愈**。

⇒ 原「让出只做一次」的建议作废：让出本就不消耗预算，改它没用。

## 三、P1-B（✅ **v56 已修**）：切页事件在 ISR 里喂狗，可能触发系统复位

**位置**：`Core/Src/main.c:1149-1152`（`hmi_on_page_enter`）

```c
void hmi_on_page_enter(int p) {
  iwdg_enable();
  iwdg_feed();          /* ← ISR 上下文调用; 内部 (HAL_GetTick()-t)>4000 时调 NVIC_SystemReset() */
```

**问题**：`iwdg_feed()` 本身会**裁决是否复位系统**。把它放在 ISR 里意味着
「任何一次屏端切页事件都能触发复位」—— 若屏端因噪声误发 `0x40~0x43`，而主循环恰已卡住 >4 s
（阻塞式串口发送 / flash 擦写），则在切页瞬间直接复位。

**修法**：~~ISR 里只`iwdg_enable()`（使能），**不调 `iwdg_feed()`**；喂狗只留在主循环。~~

> **v56 实施时采纳了更彻底的处置**：**两行一并移出ISR**（含 `iwdg_enable()`）。
> 理由：`iwdg_enable()` 会重置 `g_iwdg_t`，**等价于让 ISR 活动刷新软件狗的计时** ⇒
> 会**掩盖**「主循环已停」这一本该触发复位的真状态 —— 它和 `iwdg_feed()` 是**同一类问题**。
> v53 启用硬件 IWDG 后，喂狗点已全部在 `main()` 内（初始化 2 处 + `while` 内 2 处），
> 主循环卡住时硬件狗在 2.13~4.27 s 内独立复位，**不需要 ISR 参与**。

★ **反汇编铁证**：v56 的 `hmi_on_page_enter`（`0x08005ac4`）函数体**零 `BL` 指令**
（仅 6 条 `STRB`/`STRH` 置标志 + `BX lr`）⇒ 看门狗调用已被编译器彻底优化掉。

## 四、P2（✅ **v57 已修 · 通信回归未专项测**）：`HAL_UART_Receive_IT` 返回值被忽略（★ 原注释在说谎，见 §九.4）

**位置**：`Core/Src/main.c:209`

```c
HAL_UART_Receive_IT(huart, &rx_byte, 1);   /* 返回值未检查 */
```

若重挂失败（`HAL_BUSY` / `HAL_ERROR`）则接收链静默死亡且无任何记录。
与 P0-A 叠加时会放大故障（错误发生后重挂再失败，则彻底无路径）。

**修法**：返回值记到一个 `volatile` 标志，主循环里检测并上报/重试。

## 五、P3（✅ **v57 已修 · 真机通过**）：取消静音后最多等 2 秒才恢复鸣响

**位置**：`Core/Src/main.c` 报警处理段

```c
} else if (g_alarm != prev || (t - tlast) >= 2000u) { tjc_alarm_on(); tlast = t; }
```

报警中（`g_alarm==2`）用户点静音 → `g_mute=1`（哑音）；**再点一次**取消静音 → `g_mute=0`。

属体验瑕疵，非缺陷。若要改：把 `g_mute` 由 1→0 的跳变也纳入 `alarm_on` 的触发条件。

## 八、本次已确认无问题的项（避免重复排查）

- **UART4 vs USART3 优先级无死锁**：USART3(0) 高于 UART4(1)，两者 ISR 都是短路径（内存操作 + 置标志），无共享锁、无临界区等待
- **`rx_byte` 无竞态**：USART1 虽配了 115200 且有 ISR，但**从未使能 `USART1_IRQn`、从未调 `Receive_IT`** ⇒ 只被 USART3 一个 ISR 独占
- **ISR 内无阻塞调用**：`hmi_on_tbl_page` → `history_page_count()` 只读内存变量 `g_written`，**不碰 SPI flash**；`HAL_Delay` 仅出现在 main 与 `cal_do_factory`（均在主循环上下文）
- **`HAL_Delay` 不被饿死**：SysTick 优先级 15（最低），USART3(0)/UART4(1) 可抢占它，但 ISR 极短，SysTick 每 1 ms 必得执行
  ⚠️ 顺带订正 `main.c:74-75` 的注释推理：「SysTick 优先级低所以死锁」不准确，**准确表述是「SysTick 无法抢占 USART3 ISR，故 `uwTick` 停止递增」** —— 结论方向对，因果表述需修正
- **硬件 IWDG 当时确认未启用**（`hal_conf.h:52` 注释属实，非遗漏）
  ⚠️ **2026-10-09 更新**：此项**已于 v53 修复并启用**（`PRESC=32/RELOAD=4000`，窗口 2.13~4.27 s）。
  详见 §九.2。
- ⚠️ **本节「已确认无问题」的判断有一处漏洞（v53 真机暴露）**：§八 断言 `refill_table()` 只在「5 s 兜底」时全表重绘，
  **但测试中 `tot != s_total` 每秒成立 ⇒ 每秒全表重绘**，且每次 `HAL_UART_Transmit` 的超时上限会**逐次叠加**。
  这不是「无问题」，而是**本报告当时未识别的风险面** —— 详见 §九.3。

### 9.2 v53 修了什么（2 条 P0）

**P0-A · USART3 永久失联** —— `main.c` 新增 `HAL_UART_ErrorCallback`：`__HAL_UART_CLEAR_OREFLAG` + `hmi_get_reset()` + 重挂 `Receive_IT`。

★ **`hmi_get_reset()` 是必要配套，不是可选**：ORE 可能发生在 `get` 应答帧中途，残留半帧会让下次 `hmi_get_feed()`把帧内字节当业务命令执行 —— **历史事故：秒值 `7` → `printh 07` → 一开机就跳初始化页**。

**P0-B ·启用硬件 IWDG**（3 处，**本项目首次改 `.uvprojx`**）：

| # | 改动 |
|---|---|
| 1 | `.uvprojx` 加入 `stm32f1xx_hal_iwdg.c`（驱动本已在 `Drivers/`，只是从未编译）|
| 2 | `hal_conf.h` 解注释 `HAL_IWDG_MODULE_ENABLED` |
| 3 | `main.c` 加 `iwdg_hw_start()`（使能 LSI + `PLL_NONE`）+ `iwdg_feed()` 内加 `HAL_IWDG_Refresh()` |

参数 **PRESC=32 / RELOAD=4000 ⇒ 窗口 2.13 s(LSI 60k 最快) ~ 4.27 s(LSI 30k 最慢)**，典型 3.2 s。
`iwdg_hw_start()` **必须放在所有 `HAL_Delay`（串口冷启动 1500+1000 ms）之后**。
★ `HardFault_Handler` / `Error_Handler` 本身**仍保留 `while(1)` 未改** —— IWDG 由独立 LSI 驱动、不依赖 CPU，**硬件狗复位即可恢复**，故不需再改这两个函数。

**证据**：0 Error 0 Warning，Code 40900 → 41320，ZI 2700 → 2724（+24 = IWDG 句柄）；编译日志确认驱动入工程；axf 符号 `HAL_UART_ErrorCallback` / `iwdg_hw_start` / `hiwdg` 齐备；**反汇编铁证** `MOVS r1,#0x20`（PRER=32）+ `MOV r2,#0xfa0`（RLR=4000）+ `STRD` 连续写入 IWDG 寄存器。

### 9.3 ★★ 本报告漏判的一条 P0（v53 真机暴露，已由 v54/v55 修复）

**现象**：v53 上真机「点开始测试 → 切历史页 ⇒ 重启」，且**只重启一次**。

**「只重启一次」是决定性线索**：IWDG 启动后**不可关闭**，若真反复触发，重启后还会卡在同一处 ⇒ 应为**无限重启**。只一次 ⇒ 复位后 `g_test`（static 变量，随复位清零）不再置位 ⇒ 不再进该分支。**⇒ 证明是「单轮 `app_refresh` 阻塞 > IWDG 窗口」，不是 IWDG 配置错。**

**真因 —— 本报告 §八「已确认无问题」的判断有漏洞**：
- 历史页刷新第二条件 `tot != s_total`（`tot = g_written`）在**测试中每秒成立** ⇒ `refill_table()` **每秒全表重绘**（我原先以为注释所说「5 s 兜底」始终成立，**只在非测试期成立**）
- `refill_table()` 单次 = **24 次 flash 读 + 78 次串口发送**，正常 ≈169 ms
- 但 **`HAL_UART_Transmit` 的 100 ms 是「每次」超时** ⇒ 屏端/线路异常时 **78 × 100 = 7800 ms** ≫ 窗口 2133 ms ⇒ 硬件狗复位

**v54 三处加固**：① `refill_table` 循环内喂狗 ② `tjc_send_raw` 超时 100→20 ms（根因级）③ 测试中降频 5 s。
**v55 撤销第③ 项**（它既非必需、又牺牲实时性 —— 用户反馈「5 秒更新一次、一次更新五条」），并把喂狗由每 6 行**加密到每 2 行**。

**证据**：0E/0W，Code 41320 → 41472 → 41428；★ **反汇编铁证：15 处 `HAL_UART_Transmit` 调用的第 4 参数（r3）全部为 `0x14`=20（原 `0x64`=100）**。

★★ **方法论教训（本报告最重要的一条产出）**：
> 估算「最长阻塞时间」**不能只按理想传输耗时算**，必须叠加「**每个调用点的超时上限 × 调用次数**」。
> 凡引入硬件看门狗，先扫一遍「所有阻塞调用 × 超时上限」；
> 并新增架构约定：**启用 IWDG 后，批量刷屏类操作必须「循环内喂狗」**（后续做曲线 / 报表照此办理）。

**附带教训**：v54 我做了「三层加固」却**没评估哪一层真正必需**，结果多余的一层造成了用户可感知的代价。
★ **加固不是越多越好 —— 每加一层都要问「去掉它会不会出问题」。**

### 9.4 剩余 4 项的现状说明

**#3 P1-A（校时期间阈值按键可能被丢弃）** —— ✅ **v56 已修**。★ **但动手时发现本报告的机理描述是错的**，已在上文 §二 写入订正：

- 原写「让出连续 5 次后丢弃」→ **错**：`if (g_rtc_wait) return;` 在 `g_thr_try++` **之前**，让出**不消耗**重试预算
- 真正吃掉 5 次的是**每次 `tjc_get()` 的 500 ms 应答窗口到期**
- 真正的丢失条件 = **500 ms 窗口 < 上电期屏重建页面阻塞（约 1.8 s）**
- 修法：放弃判据改为墙钟 `THR_HI_PATIENCE_MS = 8000u`；`g_get_busy` 的清除保留（v51 起就必需，漏了 RTC 永久堵死）
- 残留风险**可自愈**：放弃边界迟到的回包会被 RTC 分支消费，但阈值 `100~1500` 与年份 `2020~2099` 不重叠 ⇒ 被 `y>=2020` 拒绝 ⇒ RTC 自动重试

⇒ 原「让出只做一次」的建议**作废**：让出本就不消耗预算，改它没用。

**#4 P1-B（ISR 里喂狗）** —— ✅ **v56 已修**，且**比原建议更彻底**：

- 原建议「保留 `iwdg_enable()`、只移 `iwdg_feed()`」→ **不够**：`iwdg_enable()` 会重置 `g_iwdg_t`，**等价于让 ISR 活动刷新软件狗计时**，会**掩盖**「主循环已停」这一本该触发复位的状态 ⇒ **同一类问题**
- 实做：**两行一并移出**。移出后全工程喂狗点只剩 `main()` 内 4 处（初始化 2 + `while` 内 2）
- 安全性**不降反升**：v53 的硬件 IWDG 由独立 LSI 驱动，主循环卡住时 2.13~4.27 s 内独立复位，不依赖 ISR
- ★ **反汇编铁证**：`hmi_on_page_enter`（`0x08005ac4`）函数体**零 `BL` 指令**（仅 6 条 `STRB`/`STRH` + `BX lr`）

**#5 P2（`Receive_IT` 返回值）** —— ✅ **v57 已修**。★ **动手时发现我上一版的判断也错了**：

- 我在 v56 里写「建议直接删掉 `g_rx_reattach_fail`，没有读取入口等于死变量」→ **错**
- v53 的置位处注释写着「**主循环会重试并可上报(不静默)**」，但**主循环从未读过它**
  （v53~v56 全程只有声明处 + 置位处2 处）⇒ **注释在说谎**
- 真正的风险：**ErrorCallback 里若重挂失败（返回非 `HAL_OK`），接收链断了且无人重挂
  ⇒ 屏幕会【第二次永久失联】**，与 P0-A 同一失效模式，只是概率低得多
  ⇒ **删掉标志 = 把「实现缺失」降级成「永久失效」**，幸好没删
- **v57 改法**：`app_refresh()` 开头加自愈重试（主循环每 250 ms 一次）——
  `__HAL_UART_CLEAR_OREFLAG` + `hmi_get_reset()` + 重挂，**直到 `HAL_OK` 才清标志、不设次数上限**
  （重试极廉价，且失败时本就没有别的路可走）
- 与 ISR 的互斥已核对：同时挂时 HAL 返回 `HAL_BUSY` ⇒ 标志保持 1 ⇒ 下一轮再试，**无需额外临界区**
- 顺带把两处注释改为已兑现的承诺（「供POST/调试观察」→「主循环消费并重试」），避免后人再据此判断它是死变量

**#6 P3（取消静音最多等 2 s）** —— ✅ **v57 已修**。改法：新增 `static uint8_t s_mute_prev`，
把 `g_mute != s_mute_prev` 纳入 `tjc_alarm_on()` 的触发条件。

**判据的精确性**：能走到该`else` 分支说明 `g_mute` **当前为 0**，
所以 `g_mute != s_mute_prev` 命中时**只可能是 1→0（取消静音）**，不会是 0→1（点静音走上面 `if (g_mute)` 分支）。
⇒ 取消静音**立即**恢复鸣响；等级变化 / 2 s 重挂 / 主动静音三条路径的行为**完全不变**。
