# 厂家设置页「数据补偿 / 比例补偿」需求评估与方案设计

> 日期：2026-10-14 ｜ 状态：**待用户确认后实施**（本文不落地任何代码）
> 需求：在厂家设置页加两个功能 —— **数据补偿**（在当前显示浓度上 ±一个数）、
> **比例补偿**（在当前显示浓度上 ×或÷一个数）。

---

## 一、结论先行

**需求本身合理，但「在当前显示浓度上做加减乘除」这个表述指向的实现方式不合理，
必须换一种落地形态，否则会踩三个坑。**

| 项 | 评估 |
|---|---|
| 功能价值 | ✅ 合理。现场微量修正确实是检漏仪的常见需求（探头批次差异、环境温漂、长期漂移） |
| 「乘除」的必要性 | ⚠️ **多余**。见 §2.2，已有 `cal_k` 就是比例系数 |
| 「加减」的位置 | ⚠️ **不能直接加减显示值**，见 §2.1 |
| 功能命名 | ⚠️ 建议改，见 §2.3 |
| 是否需要新增标定流程 | ✅ **不需要**，复用现有按键框架即可 |

---

## 二、评估：三个必须纠正的点

### 2.1 ⚠️ 不能对「显示值」加减乘除

现有数据链路（`sensor.c:114-121`）：

```c
float sensor_read_ppm(void) {
  if (g_ppm_now == 0.0f) return 0.0f;              /* 预热: 无首帧报 0 */
  float v = (float)(((int64_t)g_ppm_now * s_cal_k) / 1000 + s_cal_b);   /* ← 标定点 */
  if (v < 0.0f) v = 0.0f;
  else if (v > SENSOR_FS_PPM) v = SENSOR_FS_PPM;  /* ← 量程钳位 1500 */
  return v;
}
```

若在**显示值**上再加一层 `ppm_final = ppm_after_cal + offset`：

1. **量程被二次钳位，补偿"吃掉"**。`sensor_read_ppm()` 已把结果钳到 `[0, 1500]`。
   在其之后再加 +200，上限方向没问题，但下限方向会出问题：原始读数为 0 时先被钳成 0，
   加 +200 反而显示 200 —— 这与「洁净空气读 0」的既有语义直接冲突。
2. **报警判定与显示脱钩**。报警等级 `g_alarm` 由 `g_ppm` 算出（`main.c:961` 判断 `> SENSOR_FS_PPM`），
   补偿加在显示之后就会出现「显示 1600 但不报警」或反之的不一致。
3. **标定流程会与之打架**。零点标定执行 `PP.cal_b = -(raw * cal_k)/1000`（`main.c:1435`）
   意图是「让当前点平移到 0」。若外面还套一层加法补偿，标定完读数仍不为 0，
   用户会认为标定失败。

### 2.2 ⚠️ 「比例补偿」是重复功能

`cal_k`（0.001 定点，默认 1000 = 1.000）**本身就是比例系数**，
量程标定就是在解它：`k = span*1000/(raw1 - raw0)`（`main.c:1468`）。

再提供一个「乘除」入口，等于给同一个物理量第二个入口，代价是：
- 两处可改同一量 ⇒ 用户改完 A 忘了改 B，或两者互相覆盖，**状态机复杂度上升**；
- 量程标定会把用户手调的比例**直接冲掉**（`cal_do_span` 无条件写 `PP.cal_k`），
  用户会发现「标定完我调的系数没了」。

**建议**：比例补偿直接**复用 `cal_k`**，只提供一个「比例微调 ±」的入口（改 `cal_k`），
不新增独立字段。

### 2.3 ⚠️ 命名建议

「数据补偿」「比例补偿」在中文里都偏笼统。建议改成明确的物理含义：

| 原名 | 建议名 | 说明 |
|---|---|---|
| 数据补偿 | **零点微调**（`cal_b`, ppm） | 因为它作用的就是偏置项 b，单位是 ppm |
| 比例补偿 | **增益微调**（`cal_k`, ‰） | 因为它作用的就是斜率 k，0.001 定点 |

理由：与代码里的 `cal_b` / `cal_k` 一一对应，后续维护不会看错。

## 三、设计方案（推荐形态）

### 3.1 核心原则：补偿作用在标定链路上，不作用在显示值上

```
传感器帧 raw (ppm)
   ↓
① 硬件/零点补偿  cal_b  →  raw*k/1000 + b     ← 现有两点击定产出
   ↓
② 比例/增益微调  cal_k
   ↓
③ 量程钳位 [0, 1500]                          ← 保持在钳位【之前】
   ↓
④ g_ppm → 报警判定 / 历史落盘 / 显示          ← 单一数据源
```

**补偿值并入 `cal_k` / `cal_b`，不新增第三个环节。** 这样：
- 报警、历史、显示三者永远一致；
- 量程标定的语义不变（它仍是一次「用标气重解 k/b」）；
- 钳位只发生一次，且在所有修正之后。

### 3.2 界面与控件（复用现有布局）

厂家页现有布局规整：左侧标签（`czl_f`/`csl_f`/`cfl_f`/`czwh`/`cll15`）+
右侧按钮（`c0`/`c1`/`cf`/`cwh`/`cl15`），行距 50px，从 y=160 起排到 y=360。
下方 `y>=400` 区域**完全空着**（`p0` 已删）。

**建议在 `y=420` / `y=470` 两行新增**，与上方完全同构：

| 位置 | 标签对象 | 按钮对象 | 作用 |
|---|---|---|---|
| y=420 | `cbo` | `bbo` | 零点微调 −（`cal_b` −1 ppm） |
| y=420 右 | | `bbi` | 零点微调 +（`cal_b` +1 ppm） |
| y=470 | `cka` | `bka` | 增益微调 −（`cal_k` −5‰） |
| y=470 右 | | `bki` | 增益微调 +（`cal_k` +5‰） |

各按钮 100×40、间距 100，与 `c0`/`c1`/`cf` 同规格；标签 200×40。

### 3.3 交互设计（沿用现有防误触框架）

现有按钮框架（`main.c:91-93, 151-156`）：

```c
enum { CAL_REQ_NONE=0, CAL_REQ_ZERO, CAL_REQ_SPAN, CAL_REQ_FAC, ..., CAL_REQ_COUNT };
static uint8_t  g_restore_btn[CAL_REQ_COUNT];   /* 按下后挂起恢复计时 */
static uint32_t g_restore_t0 [CAL_REQ_COUNT];
```

新按钮**扩展进这个枚举**即可，**自动获得**：
- 按钮文本「执行中 → 默认字」自动恢复（`cal_poll` 到时改回）；
- 独立的恢复计时数组，不用新写状态机；
- 结果文案走 `crs_f`（`cal_report` 现成）。

### 3.4 步长与限幅

| 参数 | 步长 | 建议范围 | 理由 |
|---|---|---|---|
| `cal_b`（零点微调） | **1 ppm** | −500 ~ +500 | 现场微量修正粒度太细没意义、太粗易过冲 |
| `cal_k`（增益微调） | **5‰** | 500 ~ 5000 | 对应 0.5% ~ 5.0%；超出会脱离真实曲线 |

**限幅必须做**，理由与现有 `SENSOR_CAL_K_MIN/MAX`（100/10000，`sensor.h:27-28`）一致：
防止用户连点把系数推到荒谬值。

### 3.5 ★ 关键设计决策：步进是否持久化

| 方案 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| **A. 只改运行态** | 按下即改 `s_cal_k/s_cal_b`，**不落盘**，恢复出厂或重启即回标定值 | 不会污染标定数据；误操作代价极小 | 重启丢失 |
| B. 立即落盘 | 每次按下 `param_save_safe()` | 重启保留 | 会**覆盖标定结果**；连点 10 次就是 10 次 Flash 擦写 |

**推荐 A（只改运行态）**，理由：
1. 标定是「基准」，补偿是「现场微调」。**现场微调不应该改写基准**——
   出厂标定值应当可追溯，用户每次重新标定都能回到已认证的状态。
2. 本项目参数区是**追加式写、102 槽才擦一次扇区**（`param_store.c:112-118`），
   连点虽不至于立刻磨损，但会让参数区很快被微调记录塞满，
   把真正的标定记录挤出去。
3. v46 已确立设计原则：「**宁可低估，不可高估**」——对精度宁可保守，
   不要让现场随手一改就固化进产品。

⇒ 若用户确实需要重启保留，**应做成显式的「保存微调」按钮**，而不是每次按键都落盘。

### 3.6 落盘策略（若选方案 A）

- 参数结构 `param_t` **不新增字段**（复用 `cal_k`/`cal_b`）。
- 改的是运行态副本（`s_cal_k`/`s_cal_b`），**不动 `PP.cal_k`/`PP.cal_b`**。
  ⇒ `param_factory`（恢复出厂）与标定流程天然不受影响，零副作用。
- 显示当前生效值：`cst_f`（标定状态行）已经显示 `PP.cal_b`，
  建议**另加一行显示"微调后生效值"**，或把 `cst_f` 文案扩成
  「已标定 2026-10-14 补偿 -12ppm + 微调 +20ppm」。

### 3.7 命令码

协议头空位充足：`0x18`、`0x19`、`0x21`、`0x22` 均未占用。

建议：
```
HMI_CMD_CAL_B_INC = 0x21   /* cal_b +1 ppm */
HMI_CMD_CAL_B_DEC = 0x22   /* cal_b -1 ppm */
HMI_CMD_CAL_K_INC = 0x18   /* cal_k +5‰  */
HMI_CMD_CAL_K_DEC = 0x19   /* cal_k -5‰  */
```

⚠️ **必须走三字节握手**（`D5 5A NN`），与其他厂家命令一致。
依据：本项目屏口（USART3）**逐字节无过滤匹配命令码**，噪声字节等于命令码就会执行；
实测噪声分布中 `0x1A` 占 23.8%，2 字节握手仍有 0.117% 误触发率，**3 字节才 0 次**。
参考现有实现：`cf`（恢复出厂）已改单发 `D5 5A 17`。

### 3.8 屏固核对清单（实施时逐条验）

1. 两个标签 + 四个按钮 = **6 个新对象**，落在 `2.pa`（厂家页）。
2. 新对象 `id` 必须连续 `0..N-1`（现有 41 个，新增后 47）。
3. ⚠️ **改坐标必须同步 `endx`/`endy`**（`=x+w-1`/`=y+h-1`），它们才是实际命中边界，
   不同步则命中区停在旧位置、**零报错**。
4. 按钮 `up` 事件挂 `printh D5` / `printh 5A` / `printh <码>`（三行），
   **不要自己写 `txt`** —— 由固件经 `cal_report` 统一回写（与 `c0`/`c1` 同构）。
5. 屏端不得直接改 `pp2` 等全局变量来绕过固件（本项目协议是固件唯一写入方）。

## 四、与现有功能的关系（冲突检查）

| 现有功能 | 是否受影响 | 说明 |
|---|---|---|
| 零点标定 `c0` | ✅ 不受影响 | 只在标定按下时写 `PP.cal_b`；运行态微调是另一层 |
| 量程标定 `c1` | ✅ 不受影响 | 同上 |
| 硬件零点 `cwh` / 15ppm `cl15` | ✅ 不受影响 | 走 UART4，MCU 侧无交集 |
| 恢复出厂 `cf` | ✅ 不受影响 | 若采用方案 A（只改运行态），`PP.*` 不变，工厂重置照常清零 |
| 历史记录 | ✅ 不受影响 | 存的是 `g_ppm`，仍在单一数据源上 |
| 报警判定 | ✅ 不受影响 | 同上 |
| 电量曲线标定 | ✅ 不受影响 | 完全独立 |

**若选方案 B（立即落盘）**，则 ⚠️ 恢复出厂会连同微调一起清零（因为 `param_factory`
走 `dump_defaults`），且量程标定会冲掉 `cal_k` —— 这也是推荐 A 的原因之一。
