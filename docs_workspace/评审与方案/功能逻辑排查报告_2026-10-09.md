## 一、P2 · 观察项（**核心子结论已撤回**）：历史记录 `maxhead < hist_base` 判定

**位置**：`BSP/Src/history.c:59` + `BSP/Src/param_store.c:116`

```c
/* history.c:108 history_clear() */
if (found) {
  g_hist_base = maxhead + 1u;        /* 下一代起重新计数 */
  param_set_hist_base(g_hist_base);   /* ← 只推进起点, 不动任何数据 */
}
```

```c
/* history_init():59 */
if (!found || maxhead < g_hist_base) { g_written = 0; }
```

**问题**：`g_hist_base` 是「有效数据的起算代数」，而 `history_init()` 用 `maxhead < g_hist_base` 判定「无数据」。
  
只要 `maxhead` 因任何原因**倒退**到 `g_hist_base` 以下，整个历史区就会被判为空 → `g_written = 0` → 后续写入从 `idx=0` 起，**覆盖掉全部旧数据**。

**而 `maxhead` 会倒退 —— 这不是假想**：

| 触发路径                       | 机制                                                                                                                                                                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **恢复出厂后**                  | `param_factory()` (`param_store.c:101`) 保留 `hist_base` **但 `cal_do_factory` 之后 `NVIC_SystemReset()` 复位**；复位后 `history_init()` 扫到的 `maxhead` 是**旧代数**，与被保留的 `hist_base` 比较 ⇒ 若 `hist_base` 恰好等于或大于旧 `maxhead`，历史立即清零                                    |
| **参数区写满 102 槽后擦除重写**       | `param_save()` (`param_store.c:93`) 扇区写满即整扇区擦除；若此时掉电，重启后 `param_init()` 走「全无效 → 默认值」分支 ⇒ **`hist_base` 归 0** ⇒ 若 flash 里实际有更高代数的扇区，`history_init` 的 `maxhead(>0) >= hist_base(0)` 成立，此时反而正常。**反向**：`hist_base` 被写大后若参数扇区丢失 ⇒ 同上回到 0，历史**不丢**。真正危险的是下一条 |

## 二、P2 · `history_read_page()` 与 `refill_table()` 的序号在满环后会错位

**位置**：`BSP/Src/history.c:196-216`（读取）+ `Core/Src/main.c:817-820`（序号）

```c
/* main.c:817 */
uint32_t gi = (uint32_t)(page - 1u) * HIST_TBL_ROWS + (uint32_t)i;
uint32_t recnum = total - gi;               /* 行0(最新)=total */
uint32_t ser = ((recnum - 1u) % 9999u) + 1u;
```

- `total = history_total() = g_written`（**累计写入总条数，含环形覆盖，单调递增**）
- 而 `history_read_page()` 内部用的是 `avail = history_available() = min(g_written, HIST_RING_CAP)`（**环形窗口内**）

**漏洞**：一旦写满环形区（`g_written > HIST_RING_CAP = 2047×682 = 1,394,954` 条，约 **16 天**），`total` 与 `avail` 就开始分叉：

| 量                             | 满环后                | 后果                                          |
| ----------------------------- | ------------------ | ------------------------------------------- |
| `total`（用于序号）                 | 继续增长               | —                                           |
| `avail`（用于读取/页数）              | 恒为 `HIST_RING_CAP` | —                                           |
| `recnum = total - gi`         | **远大于 avail**      | **序号显示成五位数甚至更多**                            |
| `ser = ((recnum-1) % 9999)+1` | 取模后回绕              | 第 10000 条后从 0001 重新开始，**与用户预期的"累计第 N 条"不符** |

更严重的是：`history_page_count()` 用 `avail` 算总页数（正确），但 `refill_table` 的序号用 `total`。**同一页里「时间/浓度」来自 avail 窗口、「序号」来自 total 累计 —— 两个不同坐标系**，16 天后必然错位。

**现状影响**：因 `9999` 取模的存在，**不会崩溃**，只是序号语义在满环后失去意义（且未满环时正确）。属**设计瑕疵 + 潜在误解**，非当前故障。

**建议**：在 `开发进度表.md` / `HANDOVER.md` 明确写「序号为环形窗口内序号，满 139 万条后回绕」，或把序号基准也改用 `avail`。**需要用户决定取哪个语义。**

## 三、P1（**v51 已修**）：阈值键盘回读与 RTC 校时**共用同一条 `get` 应答通道**，存在串扰

**位置**：`Core/Src/main.c:209-241`

```c
void hmi_get_response(void) {
  uint32_t v = hmi_get_value();
  if (g_thr_wait) {                          /* ← 阈值回读优先 */
    g_thr_wait = 0; ... thr_apply_hi_val(v); return;
  }
  if (g_sync_st >= 2u || !g_rtc_wait) return;
  /* ... RTC 校时 */
}
```

**问题**：两个功能都发 `tjc_get(...)` 并等 `0x70` 数值帧，但**应答里不含"我是在回哪个请求"的身份信息**。`hmi_get_value()` 只有一个全局缓冲 `g_rx_buf`。

**串扰场景**：

1. 主循环 `app_refresh()` 开头先调 `rtc_time_sync_poll()`（发 RTC get，`g_rtc_wait=1`）
2. 紧接着调 `thr_hi_readback_poll()`（若此刻用户正在设置页按了键盘，`g_thr_hi_req=1`）→ 也会发一个 get
3. **两个 get 的应答都会被 `hmi_get_response()` 判给"先来的 `g_thr_wait`"**，RTC 的某个读数（如 `rY_i`=2026）可能被当成高报阈值 → `thr_apply_hi_val(2026)` → 被钳到 `THR_HI_MAX=1500` 并**落盘**

**已有缓解**：两者都是"主循环同轮串行"，实际发生概率低；且阈值回读只在用户按键盘时触发。
  
**但这不是"不可能"**：`rtc_time_sync_poll` 失败重试每 500ms 一次，校时共需 8 步（1 次探测 + 6 项 + 可能的重读），**整个过程最长可持续数秒**（`main.c:374-377` 上电还有 `HAL_Delay(1500)+1000+1000` 的串口阻塞期）⇒ **在校时窗口内进设置页按阈值键盘，就可能撞上**。

**建议**：给两条 get 加**互斥锁**——`g_thr_wait` 期间不发 RTC get，或给 `tjc_get` 加一个"请求序号"字段（屏端 `get` 回包不含序号，则退而求其次用时间窗互斥）。

## 四、P2 · 低（已复核，**判定为不成立**）：`low_batt_poll()` 上电首次的 1.25 s 延迟

**位置**：`Core/Src/main.c:547-592`

```c
static uint8_t s_lv = 0xFF, s_pend = 0xFF;
if (lv != s_pend) { s_pend = lv; s_pend_t = HAL_GetTick(); return; }  /* ← 上电第一次进这里就 return */
if (HAL_GetTick() - s_pend_t < 1000u) return;
```

**逻辑**：`s_pend` 初值 `0xFF`，首次调用时 `lv`（比如 2）与 `0xFF` 不同 ⇒ 置 `s_pend=2`、记时间、**return**。下一轮（+250ms）`lv==s_pend` 不再重置计时 ⇒ 再过 750ms 才真正下发。

**这不是 bug**（有意的"新电平需稳定 1s"），但配合 `g_page_init` 流程看：

- 上电 → 进初始化页（页3）→ `g_full_dirty=1`
- `low_batt_poll()` 首次跑要等 **1.25 s** 才下发文案
- 而初始化页倒计时有 60 s，所以**实际能看到**，无实质问题

**但有个真问题**：`s_last_play` 初值 `0`，`lv==2` 时若在 `page_full` 分支被跳过（`if (!page_full) tjc_lowbatt_play()`）⇒ 之后 `s_last_play` 已更新 ⇒ **进初始化页那 1.25 s 内若不播，之后 30 s 重播窗口从 tick 0 起算，实际会在 30 s 后补播**。行为可接受，非缺陷。

**结论**：本条**降级为"设计冗余但正确"**，仅记录，不建议改。

## 五、P0（**v50 已修**）：`selftest` 的电池检测判据**恒为真** —— 电池故障永远检测不到

**位置**：`BSP/Src/selftest.c:16`

```c
r->batt_ok = (battery_get_pct() >= 0);   /* battery_get_pct() 返回 int, 恒 >= 0 */
```

`battery_get_pct()` 的实现是 `return g_batt_pct;`（`battery.c:130`），返回值恒为 `0~100`，**永远 `>= 0`** ⇒ `batt_ok` 恒为 1。

**后果**：`hmi_update_selftest()`（`main.c:522-535`）据此拼出「自检通过」或「电池检测异常」。⇒ **电池检测这一支永远不会触发**，POST 结果行永远显示「自检通过」（绿）。

而这恰恰是**用户 10-08 刚遇到过的真实故障**（电池端子0.003V、PCM 切断）—— 那次是靠外部万用表发现的，**固件自检本应能报出来，但判据是死的**。

**建议**：给 `battery_t` 加一个"最近一次有效读数"状态（或让 `battery_poll()` 置一个 `batt_valid` 标志），`selftest` 改判该标志。**改动小、价值高。**

## 六、P0（**v50 已修**）：零点标定在**真正的洁净空气（raw=0）**下会报「非法值」失败

**位置**：`Core/Src/main.c:1022` + `BSP/Src/sensor.c:120`

```c
/* sensor.c:120 —— 注意没有像 read_ppm 那样做 0 保护 */
float sensor_read_raw(void) { return g_ppm_now; }
/* main.c:1022 */
if (raw <= 0.0f) { cal_report(CAL_REQ_ZERO, CAL_E_BADRAW); return; }   /* 文案: 标定失败：原始读数为 0，检查探头 */
```

**问题**：`raw <= 0.0f` 这个判据的**本意是"探头没接/没出数"**（评审文档 P0-3 的原意），但 `sensor_read_raw()` 返回的就是传感器报的原始浓度 —— **真正的洁净空气里传感器读数就是 0**，此时会被误判为"探头故障"，零点标定**做不了**。

**当前为何没暴露**：用户测试环境本底约 10 ppm，`raw` 不会正好为 0，所以没触发。但**这正是 v49 引导用户去做的事**（在洁净环境标定）—— 如果用户在真正洁净的 N₂ 环境或刚上电读数为 0 时标定，会撞上这个坑。

**建议**：把判据从 `raw <= 0.0f` 改为「探头是否在线」判据（`sensor_online()`，或 `sensor_warmup()`），因为`cal_precheck()` 已经检查过 `sensor_online()` 了 —— **`raw <= 0.0f` 这条判据在 `cal_do_zero` 里其实是冗余且有害的**。量程标定处（`main.c:1053`）同理（但那里 `raw1` 不可能为 0，保留无害）。

**⚠️ 这条与 v49 直接相关，建议优先修。**

## 七、P1（**v51 已修**）：`BAT_SLEW_LIMIT` 双向限幅压制充电时的上升沿

**位置**：`BSP/Src/battery.c:178-185`

限幅是**对称**的（上下都限 3%），设计意图是"抑制瞬时负载拉低"。但**充电时**电流波动会让电压忽高忽低，若出现 -5% 的瞬时跌落，限幅会把 `g_batt_pct` 强行拉低 3%，随后真实电压回升又要靠 `shown` 滞回（0.5+0.6=1.1% 门槛）慢慢爬。

**实际后果**：充电时电量显示可能**比真实值偏低最多 3%**，且恢复缓慢。用户 10-08 反馈"静置 16% / 带载 3%"的等效内阻偏大，正是这个电路特性，放大效应会被限幅进一步放大。

**建议**：限幅改为**只向下限、向上不限**（充电时不该"限快"，只该"限慢"）：

```c
if (d < -BAT_SLEW_LIMIT) g_batt_pct = last_pct - BAT_SLEW_LIMIT;   /* 只限跌 */
```

**需用户确认**——改动会让充电时的显示跳变变快。

## 十、P2 · 峰/谷值与「本次测试统计」口径不一致

### ★★ 2026-10-09 更正（用户真机反馈后，A 已实施）

用户实测「**拔电池 + 接充电器，上电仍显示「自检通过」**」—— 复查后确认**这是符合逻辑的正确行为，不是修复失效**：

- 电量采样点在 **`BAT_SW`（电池开关之后）**，不是电池座。拔电池后接充电器，充电器经 `D2(SS34)` **单向灌入** `BATTERY` ⇒ `BAT_SW` 被充到 ≈16.35V ⇒ ADC 读数有效（≫5V）⇒ 仍判「采样正常」。
- **不接充电器**时 `BAT_SW` 无电 ⇒ **屏幕根本点不亮** ⇒ 谈不上自检。

⇒ **P0-A 的修复有效，但能力边界由硬件限定**：它能报「采样异常」的唯一场景是"电池座完全悬空且无外部供电"，而那时屏幕不亮、用户看不到。**其价值是"消除恒真判据"，而非"能报出电池没插"。**
  
⇒ **"电池是否在位"软件原理上测不出**，需硬件：电池座在位检测脚（接 GPIO），或再采一路 `CHG_IN` 与 `BATTERY` 对比（占第2 个 ADC 通道，当前只用 `ADC1_IN9/PB1`）。
  
⇒ 用户裁定走方案 A：**文案「电池检测异常」→「电池采样异常」**，并在 `hmi_update_selftest()` 函数头补 5 行语义说明（明确不是"在位检测"）。屏端零改动。
  
详见 `docs/变更记录/v50_修P0_电池自检与洁净空气标定_2026-10-09.md` §六。

**建议顺序**：**A + B 先做**（都是 P0、都只改几行、且都直接命中用户当前的使用场景——A 对应 10-08 那次电池故障没被自检发现，B 对应 v49 刚引导用户去做的洁净环境标定）。C/D/E 排下一版，F/G/H 择机。
