# 标定 / 恢复出厂逻辑评审

> 基线：屏 `C4F7N_v4_fix11b.HMI` / 固件 `C4F7N_v20_firmware.hex`（2026-09-22）
> 方法：逐行读源码 + 中断优先级与 HAL 时序核算。**除标注"需真机确认"外，均为代码级确定结论。**

## 总评

**不完整、也不够合理。** 具体是四类问题：

| 类别 | 数量 | 最高级别 |
|---|---|---|
| 功能性缺陷（按了会出问题） | 3 | 🔴 P0 |
| 架构问题（上下文/时序） | 1 | 🟠 P1 |
| 数据安全 | 2 | 🟠 P1 |
| 完整性缺口（该有没有） | 6 | 🟡 P2 |

---

## 一、🔴 P0-1　**点「恢复出厂」会把设备卡死**

**代码链**：屏 `cf` 第二次点 → `printh 17` → `hmi_on_rx_byte(0x17)` → `hmi_on_cal_factory()`
→ … → **`HAL_Delay(120)`** → `NVIC_SystemReset()`

**为什么死**（三个事实相乘）：

| # | 事实 | 出处 |
|---|---|---|
| 1 | 该回调跑在 **USART3 接收中断**里（`HAL_UART_RxCpltCallback` → `hmi_on_rx_byte`） | main.c L153~162 |
| 2 | `HAL_NVIC_SetPriority(USART3_IRQn, 0, 0)` = **优先级 0（最高）**；而 `TICK_INT_PRIORITY = 15U`（**最低**） | usart.c L142 / stm32f1xx_hal_conf.h L132 |
| 3 | `HAL_Delay()` = `while ((HAL_GetTick() - tickstart) < wait) {}`，靠 SysTick 递增 `uwTick` | stm32f1xx_hal.c L382 |

SysTick（优先级 15）**无法抢占** USART3 ISR（优先级 0）→ 在中断里 `uwTick` **停止递增**
→ `HAL_Delay(120)` 的循环条件**永远成立 → 死循环**。

> HAL 源码里就写着这条警告（stm32f1xx_hal.c L115~118）：
> *"Care must be taken if HAL_Delay() is called from a peripheral ISR process,
> the Tick interrupt line must have higher priority (numerically lower) than the
> peripheral interrupt. Otherwise the caller ISR process will be blocked."*

**后果**：永久卡死，必须断电。而且**软件看门狗也救不了** —— `iwdg_feed()` 在主循环里检查 tick，
主循环进不去、tick 也冻着，所以自恢复逻辑完全失效。

> ⚠️ 注意：`param_factory(&PP,1)` 在 `HAL_Delay` **之前**就写盘了，所以断电重启后
> 出厂设置**确实生效了** —— 用户看到的现象会是「点恢复出厂后死机，断电重启后参数被恢复」。

**历史**：该写法自 **09-18 的备份起就存在**，属长期缺陷，不是最近引入。

**需真机确认**：按下「恢复出厂」的第二次 → 是否卡死？（其余无需确认，代码上无歧义）

## 二、🔴 P0-2　**零点标定的数学与量程标定不自洽**

**模型**（sensor.c）：`ppm_out = raw × cal_k / 1000 + cal_b`

| 操作 | 代码写的 | 按模型应有的 | 一致？ |
|---|---|---|---|
| 零点标定 | `cal_b = -raw` | `cal_b = -raw × cal_k / 1000` | ❌ **仅当 `cal_k = 1000` 才成立** |
| 量程标定 | `cal_k = (1000 − cal_b) × 1000 ÷ raw` | 同左（令 ppm_out=1000 解出） | ✅ |

**数值验证**（做过量程后 `cal_k ≠ 1000`）：

```
raw = 10 ppm（洁净空气残余读数）
cal_k = 1442（上一次量程标定得到）, cal_b = 0
→ 零点标定前 ppm = 10 × 1.442 + 0 = 14.4
→ 执行零点标定：cal_b = −10
→ 标定后 ppm = 10 × 1.442 − 10 = 4.42   ← 应当是 0，实际偏 +4.4 ppm
```

**根因**：零点标定里 `PP.cal_k = k`（保留斜率）却用 `b = −raw`，等于**默认斜率是 1.000**。
只有"先零点、后量程、且之后不再动零点"这一个顺序碰巧能用；**只要在量程标定之后再做零点标定，零点就永远归不了零**。

**修法（一行）**：`PP.cal_b = -(int32_t)(raw * PP.cal_k / 1000.0f);`

## 三、🔴 P0-3　零点标定**缺少"探头在线/已出数"校验**，会把零点静默清零

`sensor_read_ppm()` 的实现（sensor.c）：

```c
float sensor_read_ppm(void) {
  if (g_ppm_now == 0.0f) return 0.0f;   /* preheat: no first frame -> report 0 */
  ...
}
```

→ **没收到任何传感器帧时（探头未接 / 预热中）它恒返 0**。

而 `hmi_on_cal_zero()` 的进入判据是 `if (ppm >= 20) 失败`：
`0 < 20` → **判据通过** → `raw = sensor_read_raw() = 0` → `cal_b = 0`
→ 写盘、写「执行」（即**报成功**）。

**后果**：**探头没插的情况下点「零点标定」→ 提示成功，并把原有的零点偏移静默清零。**

**代码里明明有判据没用**：`sensor_online()`（3s 无帧判离线）、`sensor_warmup()` 都存在，标定流程一个都没调。

**修法**：零点标定入口加 `if (!sensor_online() || sensor_warmup()) { 写"未就绪"; return; }`

## 四、🟠 P1-1　整套标定**在中断上下文里做阻塞 flash 擦写**（架构问题）

| 回调里的动作 | 阻塞性质 | 量级 |
|---|---|---|
| `param_save()` → `w25q16_erase_sector` → `wait_busy()` | 忙等轮询 WIP | 4KB 扇区擦除典型 **45ms**、上限 **500ms** |
| `tjc_set_txt()` → `HAL_UART_Transmit(…, 100)` | 阻塞发送 | 9600bps 下发一条 ≈ 十几 ms |
| `app_apply_threshold()` | 同上 | ≈ 十几 ms |
| `HAL_Delay(120)` | 死锁（见 P0-1） | ∞ |

**全部发生在 USART3 接收中断里**，后果：

1. **期间屏幕发来的所有命令字节丢失**（中断被占住，后续字节无处缓冲）
2. **主循环 250ms 节拍被打断**：界面刷新、预热倒计时、状态圆点全部冻结
3. USART3(0) 优先级高于 UART4(1) → 连**传感器接收也被压住**（≈几百 ms 的帧丢失）
4. 最坏情况逼近看门狗窗口（500ms + 120ms + …，而 4s 就复位）

**对照：本项目已经有正确范式。** fix11 新增的 `0x11` 键盘回读就是按这个做的：

```
ISR: hmi_on_thr_hi_set() → 只置 g_thr_hi_req
主循环: thr_hi_readback_poll() → 发 tjc_get、超时重试
主循环: thr_apply_hi_val() → thr_commit() → 200ms 去抖后 param_save
```

→ **三个标定回调应改成同样结构**：ISR 只置 `g_cal_req = CAL_ZERO / CAL_SPAN / CAL_FAC`，
主循环里做校验、换算、落盘、发串口。这一处改动同时解决 P0-1 与 P1-1。

## 五、🟠 P1-2　`param_save()` 不是原子操作（掉电丢标定）

`param_save()` = **擦除整扇区（4KB）** → **写入 32B**。两步之间若掉电：
扇区为空白 → 下次上电 `param_init()` 校验 `magic` 失败 → **静默回默认值**，标定丢失且**没有任何提示**。

**修法**（任选）：
- 双区 A/B 交替写 + 序号，上电选 CRC 有效且序号大的那个
- 或先写到备份扇区、校验成功后再擦主区

## 六、🟡 P2　完整性缺口

| # | 缺口 | 说明 |
|---|---|---|
| 1 | **无"已标定"状态判断** | `cal_valid` 只在标定时写 1，**全码没有任何地方读它**；用过坏系数/从未标定都不提示 |
| 2 | **无标定时间戳** | 屏有 RTC 可用，却没记录标定日期 → 无法做检定/校准有效期管理（检测仪通常硬性要求） |
| 3 | **无标定失败原因分级** | 只有「执行」/「失败」两个词；「浓度超 20ppm 拒绝」和「未接入探头」无法区分 |
| 4 | 量程标定 `raw <= 0` **静默 return** | 按钮永久停在「执行中」，用户以为还在跑 |
| 5 | 标定气浓度硬编码 | `SENSOR_SPAN_PPM = 1000`；换标定气要改宏重编。且 1000 仅为满量程 (1500) 的 2/3，<1000 以外靠外推 |
| 6 | `cf.txt` 文案不随 `cfs=0` 复位 | 5.pa 的 load 只有 `cfs=0`；点一次后切页回来仍显示「确认」，再次点会直接执行 |
| 7 | 扇区 0 无写入节流/磨损均衡 | 阈值每调整一次（200ms 去抖后）擦写 4KB；擦除寿命 ~10 万次，长期频繁调阈值有量级风险 |
| 8 | `unit_mode` 死字段 | 恢复出厂的"单位复位"无任何实际效果 |

## 七、做得对的地方（建议保留）

| 项 | 说明 |
|---|---|
| 零点有洁净空气门槛 | `< 20 ppm` 才允许，防止在污染环境误标 |
| 量程有窗口 + 钳位 | 只接受 `1000 ±10%`，斜率钳到 `100~10000`，防跑飞 |
| 参数带版本 + CRC | `magic` / `version` / XOR-CRC 三重校验，结构可迁移 |
| 恢复出厂有**两段确认** | 且进设置页 `cfs=0` 自动解除，防误触（设计不错，只是文案没复位） |
| 预热期返回 0 而非满量程 | 防开机误报高浓度 |
| `0x11` 回读的 ISR+主循环范式 | 本项目已有的正确样板（见 §四） |
| 恢复出厂**不清历史记录** | 测量数据与设备设置分离，符合计量习惯（需你确认这是有意设计） |

## 八、建议的修复顺序（按性价比）

| 序 | 改动 | 行数级 | 解决 |
|---|---|---|---|
| 1 | 三个回调改为 **ISR 置标志 + 主循环执行** | 中（~40 行） | P0-1、P1-1、部分 P2 |
| 2 | 零点 `cal_b` 改为 `-raw × cal_k / 1000` | 1 行 | P0-2 |
| 3 | 零点入口加 `sensor_online() && !sensor_warmup()` 判据 | 2 行 | P0-3 |
| 4 | `param_save` 双区交替（或先写备份扇区） | 中 | P1-2 |
| 5 | 量程标定浓度可配（屏端输入或参数项） | 中 | P2-5 |
| 6 | 记录标定时间戳（用 `rtc_wall_seconds()`） | 小 | P2-2 |
| 7 | 失败原因分级文案 + `cf.txt` 复位 | 小 | P2-3、P2-6 |
| 8 | `param_save` 最小写入间隔 / 阈值离开页面再写 | 小 | P2-7 |

> **最小可用补丁**（若只想让它别死机）：把 `C4F7N_Demo/Core/Inc/stm32f1xx_hal_conf.h`
> 的 `TICK_INT_PRIORITY` 由 `15U` 改为 `0U`，SysTick 即可抢占 USART3 ISR，`HAL_Delay` 复活。
> ⚠️ 但这**只解决死机**，中断里阻塞擦写、丢命令、界面冻结仍在 —— 属治标。
