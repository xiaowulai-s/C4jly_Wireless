> ### ⚠️ 勘误（2026-09-22）
>
> 本报告初版曾断言「`rtc0..rtc5` 屏内未声明 + 固件从未赋值 → 恒 0」。**该结论错误**，现更正：
>
> `rtc0..rtc6` 是 **TJC 内置系统变量**（年/月/日/时/分/秒/星期），由**屏幕硬件 RTC 自动维护**，因此**无需在 `Program.s` 声明**——当初"未声明"的观察是对的，但推论错了。
> 官方依据：<http://wiki.tjc1688.com/variables/rtc0-rtc6.html> ——
> **「rtc0~rtc6 分别代表 年、月、日、时、分、秒、星期；rtc6 只读，根据当前年月日自动计算；需要支持 RTC 的型号才能使用；屏幕背面有电池座，默认不带 RTC 电池，需自行装入 CR1220 才能在断电时正常走时」**。
> 校时三法：①上位机联机→校准设备 RTC 时钟；②单片机向 `rtc0-rtc5` 赋值；③加时间设置页手工赋值。
>
> 因此**时间源就是屏的硬件 RTC，固件读屏时间是正确设计，不是缺陷**。真正的问题在下面第 3 节。

## 3. 🔴 核心问题：时间显示为何是死的

### 3.1 正确架构：屏硬件 RTC 是唯一时间源

```
屏硬件 RTC（需装 CR1220 电池, 断电保持走时）
   │  自动走时
   ▼
系统变量 rtc0..rtc6  (年/月/日/时/分/秒/星期; rtc6 只读)
   │
   ├─ 屏端脚本读取 ──► 显示控件 rY..rsec (页0/4/5 顶栏) / rY_i..rsec_i (页6)
   │
   └─ 固件 tjc_get 回读 ──► g_wall_epoch ──► 历史数据时间戳
```

**三个要点**（据官方 wiki <http://wiki.tjc1688.com/variables/rtc0-rtc6.html>）：

1. `rtc0..rtc5` 是**系统变量**，由屏硬件 RTC **自动走时** —— **秒不需要任何人"驱动"**
2. 屏端脚本与固件**都只读取**；`rtc6`（星期）只读，按年月日自动算
3. **校时 = 写 `rtc0..rtc5`**，三个入口任选：上位机联机校准 / 屏设置页手工设 / 固件下发

> 所以固件"时间来自屏"是**正确设计**，不是缺陷。（本报告初版误判为"两边都没定义"，已勘误，见 §0。）

### 3.2 真正的断点：设置页字段的刷新脚本丢了

页 5 的 `tm0`（实测 `en=1` / `tim=300`）定时器脚本**只有 6 行顶栏刷新**：

```
rY.val=rtc0     ← 顶栏年
rM.val=rtc1     ← 顶栏月
rD.val=rtc2
rH.val=rtc3
rMi.val=rtc4
rsec.val=rtc5
```

**少了设置字段的那 6 行**（`yr.val=rtc0` … `ss.val=rtc5`）。

而初版设计脚本 `_inject_rtc.js` 原本是**两套都刷**：

```js
function clockRefresh() { return ['rY.val=rtc0',…,'rMi.val=rtc4'].join('\n'); }
function panelRefresh() { return ['yr.val=rtc0','mo.val=rtc1','da.val=rtc2',
                                 'hh.val=rtc3','mi.val=rtc4','ss.val=rtc5'].join('\n'); }
// 定时器 = 两套都刷
setCodes(o, 'timer', clockRefresh() + (windowPage4 ? '\n' + panelRefresh() : ''));
// 页 load 也是两套都刷
cfg.pages.push({ pageCode: { load: panelRefresh + '\n' + clockRefresh + '\ntm0.en=1' } … });
```

→ 从 config 移植到 GUI 手工编辑的 fix10 时，**`panelRefresh` 那 6 行在两个地方都丢了**。

### 3.3 症状：六个字段恒为编辑器初值

`yr/mo/da/hh/mi/ss` 实测属性（页 5）：

| 对象 | 编辑器初值 `val` | `codesdown` | `codesup` | 有 load 脚本? |
|---|---|---|---|---|
| `yr` | **2026** | 空 | 空 | ❌ |
| `mo` | **1** | 空 | 空 | ❌ |
| `da` | **1** | 空 | 空 | ❌ |
| `hh` | **1** | 空 | 空 | ❌ |
| `mi` | **1** | 空 | 空 | ❌ |
| `ss` | **1** | 空 | 空 | ❌ |

→ 六个字段**从不被任何脚本写入** → 永远显示编辑器初值 = **2026 / 1 / 1 / 1 / 1 / 1**
→ **这就是你看到的「设置项显示默认 1」。** ✓

**附带发现（非缺陷）**：这 6 个字段的 `lenth`（显示位数）实测为 **0**，而顶栏同名控件设的是 `rY=4`、其余 `=2`：

| 控件 | 位置 | `lenth` | `font` |
|---|---|---|---|
| `rY` / `rM` / `rsec` | 顶栏（页0/4/5） | **4 / 2 / 2** | 0 |
| `yr` / `mo` / `ss` | 设置页字段 | **0 / 0 / 0** | 8 |

官网明确：**`length` 属性「0 为自动，最大 15 位」** —— 所以 `lenth=0` 是**合法值**，不是 bug。
但它会让月/日/时/分/秒**不补零**（显示 `1` 而非 `01`），数字宽度参差。是否统一成 4/2 **属显示风格选择**。

### 3.4 顶栏是好的 —— 可作「屏 RTC 是否在跑」的判据

顶栏 `rY..rsec` 由 `tm0` 每 300ms 从 `rtc0..rtc5` 刷新；页 6 的 `rY_i..rsec_i` 由 `tm0_i`（实测 `en=1` / `tim=300`）刷新。**这两套脚本都在，且无缺陷。**

所以分两种情况（**2026-09-22 已由用户真机确认：顶栏显示真实时间 → 屏 RTC 正常在跑**）：

| 开机后右上角顶栏 | 结论 | 该做什么 |
|---|---|---|
| **显示真实时间** ✅ **（实测即此）** | 屏 RTC 在跑 | **只需补回 §3.2 丢的那 6 行 → 设置页即正常**。固件完全不用动 |
| 显示 2000-01-01 或全 0 | 屏 RTC 没跑 | ① 查屏背面是否装了 **CR1220** 电池；② 校一次时（上位机联机→「校准设备RTC时钟」，或屏设置页设一次） |

> ✅ **已确认**：屏硬件 RTC 正常工作，`rtc0..rtc5` 有正确值。**本轮时间修复 = 纯屏端补 6 行刷新**（+ `lenth`），零固件改动。

### 3.5 次生缺陷：加减按钮的累加基准

以年份加号 `yU` 的 `up` 脚本为例：

```
yr.val=yr.val+1
if(yr.val>2099)
{
yr.val=2099
}
rtc0=yr.val
```

`yr.val=yr.val+1` 依赖「`yr.val` 已是当前 RTC 年」这个前提。

- **补回 `panelRefresh` 后前提成立**（定时器每 300ms 把 `yr.val` 同步为 `rtc0`），按钮脚本可保持不动 ✓
- 若**不加** `panelRefresh`，则必须在每个按钮开头补 `yr.val=rtc0`（先读回再运算），否则：RTC 实际 2029 时第一次点「+」得到 **2027**（基于初值 2026），且切页回来又被重置

> **推荐**：补 `panelRefresh`（还原原始设计），12 个按钮脚本不动。

### 4.1 `tjc_set_bat()` 的放大器效应

```c
const char *objs[] = { OBJ_BAT_CHIP, OBJ_BAT_CHIP_P1, OBJ_BAT_CHIP_P2, OBJ_BAT_CHIP_P3, OBJ_BAT_ROW };
```
5 个里 `pc2` / `pc2_s1` / `pc2_s2` **存在**，`pc2_s3` / `bat` **不存在**。

→ 每次电量更新发 5 帧，**2 帧打空**。在 9600bps 下每帧约 30 字节 ≈ 31ms，2 帧 ≈ **62ms 纯浪费**。

### 4.2 报警提示的替代方案：浓度大字变色（✅ 已确认可行）

`cc`（主页浓度大字，type=54 数字控件）带 `pco` 属性。官网明确：**`pco` = 字体色，可读、可通过指令修改**。

所以固件可以直接发 `cc.pco=<颜色>` 让大字随报警等级变色 —— **不需要新增任何屏控件**：

```c
/* app_refresh 里已有的报警分级 switch 旁，加一行: */
static const uint32_t ALARM_COLOR[4] = { C_STRIP_GREEN, C_STRIP_ORANGE, C_STRIP_RED, C_STRIP_RED };
tjc_set_pco(OBJ_CONC, ALARM_COLOR[g_alarm]);   /* 正常绿 / 低报橙 / 高报红 / 超量程红 */
```

与现有 `dvr` 色条逻辑（`case 2,3→RED` / `case 1→ORANGE` / `default→GREEN`）完全一致。

> ⚠️ **配色提醒**：现有 `C_STRIP_*`（绿 9771 / 橙 62689 / 红 59944）是为 **2px 色条**在深底上设计的，偏暗。
> 大字 `cc` 当前 `pco=57149`（浅紫）。用到 190px 高的字上可能需**提亮**才醒目 —— 建议实机确认后再定色。

> ✅ 若采纳此方案，**可省掉新增 `ald` 文本控件**，`OBJ_ALARM_TXT` 宏与 3 处调用可直接删除。

官方 wiki 把这条规则**重复了 8 次**强调：**「page 指令后面的代码将不会被执行」**

| 设计上应发生 | 实际 | 影响评估 |
|---|---|---|

### 5.2 🔴 新发现（2026-09-22）：`h` 的键盘绑定是残留路径，键盘输入不生效

> **勘误**：本报告初版把页 2「keybdB」判为「死代码，无调用方」，**该结论错误**。
> `h`（设置页高报阈值，数字控件）带 **`key=2`** → 绑定到页 2「keybdB」。
> 该页是**完整可用的 TJC 标准数字键盘模板**（`b0..b10` 数字/`-`/`.`、`b200` DEL、`b210` OK、`b251` X + 模板机制对象），**不是死代码**。

点 `h` 会弹出键盘；键盘 OK（`b210`）的脚本会：

```
p[loadpageid.val].b[loadcmpid.val].val=temp.val     ← 把输入写回 h.val
p[loadpageid.val].b[loadcmpid.val].txt=input.txt
page loadpageid.val                                  ← 返回设置页
```

**但这条路径实际不生效**，两个原因叠加：

| # | 事实 | 证据 |
|---|---|---|
| 1 | **固件每 250ms 无条件覆盖 `h.val`** | `main.c:594` `tjc_set_val(OBJ_THR_HI_VAL, g_thr_hi);` 在 `app_refresh()` 的主页刷新块（571–613）内，**没有任何页面/条件守卫** → 键盘写入的值 **≤250ms 被冲回原值** |
| 2 | **固件从不回读 `h.val`** | 全固件只有 `tjc_get("rsec_i"/RTC_MIRROR…)`，**没有**对 `h`/`l` 的 `tjc_get` → 就算不被覆盖，MCU 也不知道用户改了什么 |

**旁证**：`hmi_callback.c` 头部注释仍留着**旧方案**：

> 「阈值(0x11/0x12)只发码, 值在屏内 h/l; 会话收到后应 tjc_get 回读 h.val/l.val」

说明早期设计是「键盘改 `h.val` → 屏发码 → MCU 回读」，后来演化为 `hm`/`hp` 按钮（`0x02`/`0x03` 自增自减）方案，**键盘绑定 `key=2` 成了残留**。

**结论**：`hm`/`hp` 按钮是**唯一有效**的高报阈值调节方式。键盘弹出后改值不会生效，用户会以为"改了没用"。

**三种处置**（待决策）：
- **A** 保留现状 —— 零改动，但键盘是个"假入口"
- **B** 修通键盘 —— 恢复旧方案的 `0x11` 回读链路（键盘 OK 加 `printh 11`，固件加 `tjc_get("h")`，并把 250ms 无条件写改为 `g_thr_dirty` 时才写）
- **C** 解除绑定 —— `h.key` 置 255，页 2 成为真正的死页（是否删页需另行评估 ID 重编号风险）

### ⚠️⚠️ 工具限制（2026-09-22 发现，影响所有脚本分析）

`lib/page.js` 的 `readObj()` 用 **`L >= 16 ⇒ attr`** 这一朴素启发式区分「属性记录」与「脚本行」。
**但脚本行也可以 ≥16 字节** → 这类行会被误判成 `attr`，导致：

- 脚本内容被**截断**（首 16 字节当属性名，其余当值）
- `codesXX-N` 声明的**行数与实际读到的行数不符** ← 这是识别该问题的信号

**本工程受影响范围**：**仅页 2「keybdB」**（模板行普遍 20–93 字节）。
页 0/4/5/6 的脚本行最长 <16 字节，**分析结论不受影响** ✓
（页 4 的 `ptg` 有 2 行 16/18 字节，但未被本报告引用）

**正确读法**：按 `codesXX-N` 声明的行数逐条取，不要用长度判定。
→ 已提供 `_script_dump_bycount.js`（按声明行数读，并标注每行字节数）。

> **对 `AGENTS.md` §3「脚本单行 ≤15 字节，≥16 被当 attr 解析 → 引擎崩溃」的补充**：
> 本次证据表明 —— **TJC 原厂自带的键盘模板本身就含 20~93 字节的脚本行**，且该页在工程中长期存在。
> 因此「≥16 字节 ⇒ 引擎崩溃」**很可能不成立**；更准确的表述是
> **「≥16 字节 ⇒ 我们的解析工具会误判」**。
> ⚠️ 但**建议仍沿用 ≤15 字节的写法**：改脚本的工具（`page.set`/`setCodes` 等）都基于该启发式，
> 一旦写入长行，后续工具链的分析/修改会出错。**属"对工具保守"，不是"对引擎保守"**。

### ⚠️ 需你知悉的副作用

- **低报阈值将不可调、也不可见**（`l` 数值控件与 `thv` 文字都删）。
  低报**报警功能本身仍工作**（`g_alarm==1`），阈值固定为参数默认值 `PP.thr_lo`。
  将来若要调，需重编固件或改参数区。
- 报警提示只剩**颜色**一个通道（大字变色 + `dvr` 色条）。色觉障碍用户可能不易分辨 ——
  190px 大字的紫→红变化很明显，但若后续想加文字，需在主页新增控件。
- **高报阈值 `h` 改为"仅条件写"后**，其界面值不再每 250ms 刷新。若某条路径漏了下发，
  屏上会显示**陈旧阈值**（固件内部值仍正确）。已覆盖的路径：开机 `app_apply_threshold()`、
  `g_thr_dirty`、进设置页（依赖 1-3 修好）、键盘改完（依赖 2-9）。**需真机回归确认无遗漏**。
