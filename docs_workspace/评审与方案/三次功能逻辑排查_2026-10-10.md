## 一、P0-A（✅ **v58 已修**）：`history_clear()` 后 `PP.hist_base` 从不更新 → 任意一次参数保存都会把清空标记写回旧值

### 1.1 位置

| 文件 | 行 | 内容 |
|---|---|---|
| `history.c` | 121-122 | `g_hist_base = maxhead + 1u; param_set_hist_base(g_hist_base);` |
| `param_store.c` | 116-122 | `param_set_hist_base()` 用**局部变量 `t`** 写 flash |
| `param_store.c` | 85 | `param_save()` 的 `param_t tmp = *p;` —— 把调用者的**整个结构体**写进新槽 |
| `main.c` | 428 | `param_init(&PP)` —— **只在开机时执行一次**，此后 `PP` 再不刷新 |

### 1.2 机理（已逐行复核）

`history_clear()` 推进的是 **`history.c` 的静态变量 `g_hist_base`**，而落盘走 `param_set_hist_base()`，后者声明了局部 `param_t t` 并只改 `t.hist_base`：

```c
void param_set_hist_base(uint32_t base) {
  param_t t;          /* ← 局部副本 */
  param_init(&t);
  t.hist_base = base;
  param_save(&t);     /* ← 只把这张副本写进 flash */
}
```

⇒ **全局 `PP.hist_base` 从头到尾没被更新**，仍是开机时的旧值。

随后任何一次 `param_save(&PP)`（`param_save_safe()` → `param_save(&PP)`，`main.c:590`）都会
`tmp = *p` 把**旧 hist_base** 连同新阈值一起写进新槽 ⇒ **刚写入的清空标记被覆盖**。

### 1.3 后果链（致命）

1. flash 中 `hist_base` 被打回旧值（可能是 0），但历史区各扇区 head 里存的仍是**绝对代数**（≥1）
2. 下次开机 `history_init()` 算出 `gen = maxhead - hist_base`，比正确值**少 1**
3. `ps = gen % HIST_SECTORS` 指向**错误扇区**——真实数据在扇区 0，它去读扇区 1
4. 扇区 1 是空的（全 `0xFF`）⇒ `sz = 0` ⇒ `g_written = gen*682 + 0` —— **数字虚高**（真实可能只有 50 条）
5. `history_available()` 不截断到实际值 ⇒ UI 宣称数百条、`page_count` 显示数十页
6. 之后 `history_log()` 从该虚高 idx 继续写，触发 `history.c:90` 的整扇区擦除 ⇒ **开始逐步擦除真实历史数据**

### 1.4 触发条件（真机三步，**无需掉电**）

1. 历史页点「清空历史」（`hist_base: 0 → 1` 落盘，运行时 `PP.hist_base` 仍为 0）
2. **任意一次参数保存** —— 设置页按一次 `+`/`-` 改阈值、或做一次标定、或恢复出厂
3. 重新上电

⇒ 历史总条数错乱 + 表格显示错位数据 + 后续记录覆盖真实历史。

### 1.5 ★ 加重因素（我在复核时额外发现，原报告未提）

`main.c:1203` 恢复出厂的实现是：

```c
param_factory(&PP, 1);       /* 保留 hist_base -> 不撤销"清空历史" */
```

而 `param_factory()`（`param_store.c:101-107`）做的正是 `uint32_t hb = p->hist_base;` ——
**它"精心保留"的正是那个陈旧值**。

⇒ 所以**恢复出厂不但不会修正它，还会把陈旧值再次固化到 flash**，让错位更难恢复。

### 1.6 修法

最小改动：`history_clear()` 里同步 `PP.hist_base`。但 `history.c` 不该认识 `PP`（BSP 层不认识业务层），**推荐改在 `main.c` 侧** —— `hist_clear_poll()` 调完 `history_clear()` 后补一句 `PP.hist_base = history_get_base();`（需 `history.h` 导出一个 getter）。

更彻底的做法：`param_save()` 改为**只更新易失字段**，不带 `hist_base`（需拆分写入路径）。

## 二、P0-B（✅ **v59 已修 · 方案方向已修正**）：102 槽写满触发整扇区擦除，擦除窗口内掉电 ⇒ 标定与阈值静默回默认值

### 2.1 位置

`param_store.c:92-96`：

```c
slot = find_free_slot();
if (slot >= PARAM_SLOTS) {        /* 已写满 102 槽 -> 擦扇区后从首槽重来 */
  w25q16_erase_sector(PARAM_FLASH_ADDR);   /* ← 整扇区擦除, 最坏约 400 ms */
  slot = 0;
}
```

### 2.2 与注释的承诺**直接矛盾**

`param_store.c:5-6` 的注释原文：

> 写满才擦一次扇区。掉电最多丢最后一条, 旧记录仍在, **不会静默回默认值**。

这句话**只在追加写的第 1~102 次成立**。第 103 次保存走的是"先擦整扇区再重写"，擦除窗口内掉电 ⇒ 参数区空白 ⇒ `param_init()` 倒序扫 102 槽全部失配 ⇒ 走 `dump_defaults()` + 重新擦写。

### 2.3 恢复得回来吗

**能自洽恢复，不会卡死**（这点必须说清楚，避免过度恐慌）—— 但**恢复值是出厂默认值，用户无任何提示**：

| 字段 | 恢复值 | 用户实际设置 | 后果 |
|---|---|---|---|
| `cal_k` / `cal_b` | 1000 / 0 | 标定值 | **浓度读数错误，检漏仪失准** |
| `cal_valid` | 0 | 1 | 标定状态被抹掉 |
| `thr_hi` / `thr_lo` | 500 / 100 | 用户阈值 | **报警门限被静默改回** |

对燃气检漏仪而言，**静默丢失标定 = 测量结果不可信，且用户无从察觉**。

### 2.4 触发条件

**前置**：累计 102 次 `param_save`。消耗槽位的入口有五类 —— 每次阈值 `+`/`-`（`main.c:975-978`）、每次零点标定（`main.c:1154`）、每次量程标定（`main.c:1193`）、**每次「清空历史」**（`param_store.c:121`）、恢复出厂（`main.c:1203`）。正常使用下跨年度必然达到。

**叠加**：第 103 次保存的擦除窗口（最坏 ~400 ms）内掉电。
⇒ 表现为「偶尔某次设置没保存成功」，实为整表丢失 + 标定归零。

### 2.5 修法

真正的解是**让 `hist_base` 与易失参数分处不同扇区**（见 P1-A），
或引入**双副本 + 世代号**，使擦除窗口内仍有一份有效副本存活。

短期可做的**减损**：写满时**不要擦整个扇区**，而是先把最新一条写到「保留槽」区（扇区末尾预留 1~2 槽永不参与轮转），
擦除期间以保留槽为准；擦除成功后再把保留槽的内容追加到主区。这样掉电最多丢"本次设置"，而非"全部历史设置 + 标定"。

## 三、P1-A：`hist_base` 与易失参数同扇区 ⇒ 参数区失效同样引发 P0-A 的错位

### 3.1 机理

P0-B 的擦除窗口还有一个**次生后果，比标定丢失更隐蔽**：

`dump_defaults()`（`param_store.c`）会把 `hist_base` 归 0。若掉电时 `hist_base` 恰好**非 0**（用户清过历史），
恢复默认值就把它归 0 ⇒ 与 P0-A **完全相同的 `gen` 错位** ⇒ 历史数据错乱 + 逐步擦除。

### 3.2 根因是设计耦合

**逻辑清空的起算点（`hist_base`）与高频改写的阈值/标定共处扇区 0，共享同一个擦除窗口和同一条失效路径。**

⇒ 这条与 P0-A、P0-B 指向同一个根因：**参数区把"高频改写的易失参数"与"历史区的逻辑基准"混在同一个 4 KB 扇区**。

**修法**：把 `hist_base` 迁到历史区自身的头部（如扇区 1 的前 4 字节），彻底解耦。

## 四、P1-B（✅ **v58 已修**）：13 个跨 ISR/主循环的变量**缺 `volatile`**（含我自己 v56 引入的 1 个）

### 4.1 事实

`hmi_on_rx_byte()`（`Middleware/Src/hmi_callback.c`）在 **USART3 ISR 上下文**里直接回调各处理函数，
而这些函数**直接写若干全局变量**（没有"只置标志"的中转）。逐个核对声明：

**已正确加 `volatile` 的**（说明这套约定在本项目是明确执行的）：

| 变量 | 写入方 |
|---|---|
| `g_cal_req` / `g_hist_clear_req` | `hmi_on_cal_*` / `hmi_on_hist_clear` |
| `g_thr_hi_req` / `g_thr_try` / `g_thr_wait` | `hmi_on_thr_hi_set` |
| `g_get_busy` / `g_rtc_wait` / `g_sync_*` / `g_time_sync_idx` | `hmi_get_response` |
| `g_rx_reattach_fail` | `HAL_UART_ErrorCallback`（v53）|
| `g_page_now` / `g_full_dirty` / `g_cal_st_dirty` / `g_thr_push` / `g_refill_req` | `hmi_on_page_enter` |
| `g_mute` | `hmi_on_buz_mute` |

**★ 缺 `volatile` 的 9 个**（本条缺陷）：

| 变量 | 写入方（ISR） | 读取方（主循环） | 引入时间 |
|---|---|---|---|
| **`g_thr_t0`** | `hmi_on_thr_hi_set` | `thr_hi_readback_poll`（8 s 耐心判据）| **v56（我引入的）** |
| `g_thr_dirty` | `thr_commit` ← `hmi_on_thr_hi_inc/dec` | `while(1)` L472 | 长期 |
| `g_save_pending` | 同上 | `while(1)` L473 | 长期 |
| `g_thr_dirty_t` | 同上 | `while(1)` L473 | 长期 |
| `g_test` | `hmi_on_test_toggle` | 多处判测试中 | 长期 |
| `g_test_t0` | `hmi_on_test_toggle` | 统计窗口 | 长期 |
| `g_peak` / `g_min` | `hmi_on_test_toggle` | 首页显示 | 长期 |
| `g_sess_sum` / `g_sess_cnt` / `g_sess_max` / `g_sess_min` | `hmi_on_test_toggle` | 统计显示 | 长期 |
| `g_tbl_page` | `hmi_on_tbl_page` | `refill_table` 判页 | 长期 |

★ **`g_thr_t0` 是我v56 自己引入的**：`hmi_on_thr_hi_set()` 在 ISR 里写它、`thr_hi_readback_poll()` 在主循环读它判超时。
同一函数里紧邻的 `g_thr_hi_req` / `g_thr_try` 都加了 `volatile`，**唯独漏了它** —— 这是我的疏忽，不是历史遗留。

### 4.2 实际风险分级（区分「撕裂」与「编译器优化」）

| 项 | 风险 | 说明 |
|---|---|---|
| 字节撕裂 | **低** | `uint32_t` 在 Cortex-M3 上对齐访问是单指令 `STR`/`LDR`，不会真的撕裂；`uint8_t` 天然不可撕裂 |
| **编译器优化** | **中** | 缺 `volatile` 时，编译器**有权**把主循环里的多次读缓存到寄存器、或把 ISR 的写视为不可见而优化掉 |
| `g_sess_sum` 是 `uint64_t` | **注意** | 64 位读**非原子**（需两次 `LDR`），理论上可能读到撕裂值；但仅用于显示统计，最坏是一帧显示乱数 |

⇒ 归为 **P1**（不是 P0）：撕裂风险被硬件对齐消除了，**真实风险是"判据可能读到陈旧值"**。
后果举例：`g_test` 若被主循环读到陈旧的 0，则测试中不写历史记录；`g_tbl_page` 陈旧则翻页显示错乱。

### 4.3 修法

给这 9 个变量加 `volatile`（逐个确认写方确实在 ISR，**不要盲加**——本项目已有 16 个变量正确加了 `volatile`，
说明当初是按"谁在 ISR 写"逐个判定的，这批是遗漏）。

★ **我这次的排查方法**（可复用）：用正则扫出全部"`static` 声明 + 多处出现 + 缺 volatile"的变量（约 27 个），
再**逐个核实其写入方是否真在 ISR 上下文**，最终只有这 9 个成立。**其余 18 个是纯主循环变量，属误报。**

★ 同批误报中特别值得一提的两个：我一度怀疑 `g_cal0_armed` / `g_cal0_t0` / `g_cal0_ppm0`（v49 的零点两步确认状态）跨 ISR，
**核实后确认它们全部由 `cal_do_zero/span/factory`（主循环）读写** —— ISR 侧的 `hmi_on_cal_zero()` 只置 `g_cal_req`。
**又一次"未读代码就下结论"，第三次了。**

## 六、已复核无问题的项（避免重复排查）

**`param_store`**
- `sizeof(param_t) == 40`、`PARAM_SLOTS == 102`（`4096/40`）—— 与 `param_store.h` 一致
- CRC 覆盖 36 字节，**无空洞**（结构体无 padding，`crc` 在偏移 36~39 被排除）
- ★ **CRC 别名效应被 `magic` 校验完全抵消**：算法 `c ^= b[i]; c = rotl32(c,1)` 的别名对恰为 (0,32)(1,33)(2,34)(3,35)，**四对全部涉及 `magic` 字节** → 任何利用别名构造的碰撞都会同时破坏 `magic` ⇒ 被 `param_store.c:72` 独立拦截。残余风险需协同篡改 3 字节以上，自然位衰不会产生
- 写入序列合规：追加写目标槽必为全 `0xFF`（已擦态）；回绕与恢复路径都是先擦后写
- 40 B 记录**跨 256 B 页边界**时，`w25q16.c:98-107` 的 offset/chunk 拆分正确，每次 `page_program` 各带 `write_enable`
- 撕裂写留下的"非空白但 CRC 失配"槽：不占 `find_free_slot`（浪费一槽）、不被 `param_init` 采信（回退上一槽）⇒ **行为安全**

**`history`**
- `HIST_CAP = 682` 来源 `(4096-4)/6` 与写入逻辑自洽；`REC_ADDR(681)+6 = 4096` 恰好末字节不越界
- 历史区 `SECTOR_ADDR(2046)+4096 = 0x800000` 恰好 8 MB，不越出 W25Q64，不与参数区重叠
- **空扇区 `0xFF` 不会被当作有效数据** → `rec_is_empty` → `history_read_one` 返回 0 → `read_page` break → `main.c` 填空格
- 「清空后不写新记录」时 `maxhead < hist_base` 每次成立、`g_written` 每次归零 —— **符合清空语义，不是缺陷**
- 连续两次清空（中间无新记录）**幂等**
- `(recnum-1) % 9999 + 1` **无下溢**（`avail ≤ total` 保证 `recnum ≥ 1`）、**无回绕错误**（需 136 年）；`% 9999` 是屏端 `sn` 控件 4 位容量的折中，内部计数单调
- 整数溢出（`g_written` 回绕 / `seq` 撞 `SEQ_EMPTY`）—— 均需 ≥136 年，理论不可达
- `history_clear()` 在**主循环上下文**执行（`main.c:1230`），ISR 侧只置标志，符合约定
- `history_clear` 最长路径（2047 次读 ≈123 ms + 参数区 2 次全扫 ≈12 ms + 扇区擦除 ≤400 ms ≈ **535 ms**）< IWDG 3.2 s ⇒ **不触发复位**

**并发/ISR**
- `g_rx_reattach_fail` **有** `volatile`（我的正则一度误报，已核实）
- 全工程喂狗点全部在 `main()` 内（v56 已移出 ISR），ISR 内 0 处
- `thr_commit()` 只置标志，实际 flash 写在主循环 —— **fix12"回调只置标志"约定贯彻一致**（这点做得很好）

## 七、优先级建议

## 八、一条方法论教训

**这轮的 3 条数据丢失缺陷（P0-A / P0-B / P1-A），前三轮排查全部漏过。**

原因：**前几轮都从「运行时逻辑正确性」入手**，而这几条缺陷只在**掉电 / 长期使用 / 清空后改设置**这类**跨会话场景**下才显形。
运行一次设备看不出任何异常。

★ **教训：嵌入式排查不能只验「功能对不对」，还要问「状态能不能活过一整天的使用周期」。**
存储层的追加/回绕/擦除窗口、代数基准的一致性，是这类设备的固有高风险面 —— 应作为独立的一轮排查主题，
而不是作为 `param_store.c` 阅读时的附带产出。

★ 另一条：**前两轮我曾两次因「未读代码就下结论」而误报**（首轮 D 项以为屏端缺二次确认、二次 P2 以为标志是死变量）。
本轮派 agent 做存储层审查后，**我对它的每条结论都逐行复核了源码**（`history_clear` / `param_set_hist_base` / `param_save` / `param_factory` / `param_init` / `dump_defaults`），确认全部成立后才写入报告 —— 这个纪律是本轮没再出现误报的原因。
