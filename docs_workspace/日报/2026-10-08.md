## 三、核心结论

### 1. 充电管理：三处硬伤，其中两处是「电压顶死」类

- **★ 头号硬伤——16.8V 适配器与 4S 电压顶死**：Buck 需输入高于满充电压才能降压；CV 末期电池 16.8V = 输入 16.8V → 占空比 100% → **退化成直充，CC/CV 限流失效**（恰是最易过压的阶段）。多份厂商资料一致要求"输入 ≥ 满充电压 + 0.8V"
- **★ 二号——SS34 串在充电路径**：`16.8V 适配器 → F1 → D1(SMBJ24A) → D2(SS34) → BATTERY`，肖特基 VF≈0.45V ⇒ **电池实际只充到 16.35V** ⇒ 长期欠充。⚠️ **固件 `BAT_FULL_V=16.3V` 其实是在迁就这个硬件缺陷**
- **★ 因此：单纯换 19V 适配器更危险**（19−0.45 = 18.55V vs 上限 16.8V）→ 必须 **19V + 4S Buck CC/CV，且 SS34 移到 Buck 输入侧**
- **CV 定为 16.7V 的理由**：PCM 过充阈值公开资料有 **16.8V±0.05V** 与 **4.25V×4=17.0V** 两种说法，取**交集 16.7V**——两种情况都不触发 PCM，容量代价仅 0.6%
- 电池 **CNGK4S7800**（4S3P 18650 / 14.8V / 7800mAh / 标准充 0.2C / **充电温度 0~45°C ⇒ NTC 必需**）

### 2. 电量显示虚高 27 个百分点 —— 「显示 30% 关机」的真因

用户实测三数据构成铁证：电池端子 **0.003V**（PCM 切断放电）· 插充电线 → **14V**（充电解锁 PCM，电池本体完好）· **LED2 通电即亮**（5V正常）。

- `battery.c` 用 **12.0~16.3V 线性映射**穿过锂电池"缓降→陡降"曲线，实测 13.76V 真实仅约 15% ⇒ **"显示 30% 关机"实为真实只剩 5~8%**，静默状态那 0.17A 足够把它推到 PCM 阈值下 ⇒ **不是死机，是电池真没电了**
- ⚠️ **顺带实测确认**：电量测的是**带载**电压（`BAT_SW` 分压，非开路电压）—— 本次**静置 16% / 带载 3%**，反推等效内阻 0.24~1.15 Ω/节 = **正常新品的数倍**，与"PCM 切断 + 寿命末期"互相印证
-⇒ 用户疑问"高电量时初始化页会不会误报低电"**不成立**：`battery.c` 首采**直通不滤波**（`g_filt_first`），首帧直接是 3%（非100%）⇒ **不会误报**
- **→ 根治仍是换电池**；软件侧只能把曲线改对

### 3. 排查过程中我自己判错的三次（都被数据推翻）

| # | 我的错误结论 | 被什么推翻 |
|---|---|---|
| 1 | "LED 不亮 ⇒ 5V/3.3V 缺失" | 原理图：两灯都是 MCU GPIO 驱动，而固件**零 LED 控制代码**；用户实测"通电即亮" |
| 2 | "泵启动冲击 → 过流误触发过放" | 用户："关机时为静默状态，未启动传感器和泵" ⇒ 仅 0.17A，距阈值差 20 倍 |
| 3 | "充电 = CHG_5V 经 SS34 直充" → 又据旧文档改口说是 MT3608 升压二极管 | **两者都不对**：旧文档（TP4056+MT3608+18650×2）对现板不适用，现板 D2 就是充电路径 |

### 4. v49：零点标定的安全盲区

用户在**户外**标定（本底约 10ppm）。原逻辑只判 `ppm < 50ppm` ⇒ **户外 10ppm 直接通过并被写成零点** ⇒ 真实 10~25ppm 的泄漏会显示 0。两步确认方案：

| 步骤 | 按钮 `c0` | 右栏 `crs_s1` | 写Flash |
|---|---|---|---|
| ①第一次点击 | `待确认` | `当前 10ppm，须洁净空气，3秒内再按确认` | ❌ |
| ②3s 内再点、浓度未变 | `执行` | `零点标定完成 补偿-12ppm，请确认环境洁净` | ✅ |

| ④超 3s 再点 | 回到 ① | — | ❌ |

## 五、踩坑与教训（6 条）

1. **核对屏显文案必须做字节级解码，不能看注释** —— 我拿源码注释当答案写成「电量低请充电」，被用户报告的才对；`_cfg_lowbatt.js` 用 `\\xNN` 转义时若经二次处理会出问题
2. **块注释内不能写 `/* ... */`** —— 会让注释提前闭合 → 语法错乱 → 报 `source file is not valid UTF-8`（**编码本身完好**，U+FFFD=0，别误判为编码损坏）。修法：块内只用 `[]`
3. **不能用"镜像/axf 搜 GBK 文案"举证所有改动** —— `low_batt_poll()` 的文案是 `\xNN` 转义写法，AC6 用 MOVW/MOVT 逐字压栈、**不存连续字节**；此类改动改用 `fromelf --text -c` 看立即数
4. **hex 展开脚本要用连续字节流**（只取 type=0 数据段、不做地址映射）；若按 `typ=4` 算扩展基址会得到 134MB 的荒谬镜像长，使常量搜索失效
5. **hex 校验和上界是「整行到行尾」** —— 写成 `9+2n`（漏 CC）或 `4+2n`（漏一半数据）会报假损坏
6. **主循环里长阻塞操作会挤掉后续请求** —— `history_log()` 写 W25Q64 扇区擦除典型 400ms~最坏 3s，而软件看门狗 `iwdg_feed()` 阈值 **4 秒**（真 IWDG 未启用，`hal_conf.h:52` 被注释）⇒ 可能逼近阈值触发复位，表现为"无法开机"
