## 二、P2 · `g_rx_reattach_fail` —— ★ 我上一版的判断错了

### 2.1 错在哪

我在 v56 变更记录里写「建议**直接删掉**标志，没有读取入口等于死变量」。

**读代码后发现：这条注释在说谎。**

```c
/* v53 原文 */
if (HAL_UART_Receive_IT(huart, &rx_byte, 1) != HAL_OK) {
  g_rx_reattach_fail = 1;        /* 主循环会重试并可上报(不静默) */
}
```

注释承诺「主循环会重试」—— 但**主循环从未读过它**（v53~v56 全程只有声明处 + 置位处，共 2 处）。

⇒ 所以问题**不是"死变量"**，而是：
**ErrorCallback 里若重挂失败（返回非 `HAL_OK`），接收链就断了且无人重挂
⇒ 屏幕会【第二次永久失联】** —— 与 P0-A 同一失效模式，只是概率低得多。

**删掉标志 = 把一个"实现缺失"降级成"永久失效"。** 幸好没删。

### 2.2 改法：让标志真正被消费

`app_refresh()` 开头（主循环每 250 ms 调用一次）加自愈重试：

```c
if (g_rx_reattach_fail) {
  __HAL_UART_CLEAR_OREFLAG(&huart3);
  hmi_get_reset();                                  /* 仍要丢残留半帧 */
  if (HAL_UART_Receive_IT(&huart3, &rx_byte, 1) == HAL_OK) g_rx_reattach_fail = 0;
}
```

**为什么不设次数上限**：重试本身极廉价（只是发起一次单字节接收请求，不发送任何数据），
而「失败就一直重试」比「重试 N 次后放弃」更符合设备应 self-heal 的定位 —— 反正失败时也没有别的路可走。

**与 ISR 的互斥性**（已核对，无需额外临界区）：
- 若主循环重挂成功 ⇒ 标志清零，ISR 的 `RxCpltCallback` 正常接管后续字节
- 若与 ISR 同时挂 ⇒ HAL 返回 `HAL_BUSY`，标志保持 1，下一轮再试
- `hmi_get_reset()` 幂等，多调无副作用

### 2.3 顺带订正注释

`g_rx_reattach_fail` 的声明注释由「供 POST/调试观察」改为「主循环消费并重试」，
置位处注释由「主循环会重试并可上报」改为「置位: app_refresh 每轮会重试直到成功」——
**把已经兑现的承诺写准确**，避免后人再据此判断它是死变量。

## 三、P3 · 取消静音后最多等 2 秒才恢复鸣响

### 3.1 原判据

```c
} else if (g_alarm != prev || (t - tlast) >= 2000u) { tjc_alarm_on(); tlast = t; }
```

取消静音时（`g_mute` 由 1 → 0）：`g_alarm` 仍 == `prev`（还是 2），距上次 `alarm_on` 通常不足 2 s
⇒ **两个条件都不满足 ⇒ 最多哑音 2 秒**。

### 3.2 改法：把 `g_mute` 的跳变纳入判据

```c
static uint8_t s_mute_prev = 0;                                  /* 上轮的 g_mute */
...
} else if (g_alarm != prev || (t - tlast) >= 2000u
           || g_mute != s_mute_prev) {        /* ← 新增 */
  tjc_alarm_on(); tlast = t;
}
...
prev = g_alarm;
s_mute_prev = g_mute;
```

**为什么这个条件精确**：能走到这个 `else` 分支说明 `g_mute` **当前为 0**，
所以 `g_mute != s_mute_prev` 命中时**只可能是 1 → 0（取消静音）**，不会是 0 → 1（点静音 —— 那种情况走上面的 `if (g_mute)` 分支）。

⇒ 取消静音**立即**恢复鸣响；其余路径（等级变化、2 s 重挂、主动静音）的行为**完全不变**。
