## 一、共 3 类结构缺陷、11 处修复

### 缺陷 1：对象体 `end`(0x00000000) 终止记录不在末尾 —— 3 处

**成因**：`build_v9_factory_page.js` 清理旧脚本时用

```js
items.filter(it => it.kind !== 'mark')   // ★ 把 end 终止记录也留下了
```

随后 `push` 的脚本行落在 `end` **之后**：

```
[...属性, end, "codesdown-1","tmr1.en=1","codesup-1","tmr1.en=0"]
                     ↑ 残留字节被编辑器当成下一个对象的记录 -> objedit ref error
```

**位置**：`5.pa#60 fw` / `5.pa#76 tmr1` / `2.pa#36 bk`。v8 基线 **0 处**。

**修复**：把 `end` 之后的记录移到 `end` 之前（`fix_page_end.js`）。

### 缺陷 2：对象缺 `att-NN` 属性模板标识 —— 2 处

**成因**：`lib/page.js` 把 `att-NN` 归类为普通 mark，所以缺陷 1 那个 filter 会把它一起删掉。

`att-NN` 是对象体的**第一行**，编辑器据此知道该控件有哪些属性。缺了 → objedit ref error。

**证据**：v8 全工程 6 页 **350 个对象无一例外**都有 `att-NN`。

**位置**：`5.pa#76 tmr1`（缺 att-9）、`2.pa#36 bk`（缺 att-42）。v8 基线 **0 处**。

**修复**：按 type→att 映射表补回首行（`fix_att.js`）。

**type→att 映射表**（v8 全工程一一对应，无歧义）：

| type | att-NN | 控件 |
|---|---|---|
| 51 | att-9 | 定时器 |
| 52 | att-11 | — |
| 53 | att-42 | — |
| 54 | att-39 | — |
| 98 | att-42 | 按钮 |
| 112 | att-22 | — |
| 116 | att-39 | 文本 |
| 121 | att-28 | 页 |
| 1 | att-39 | — |

### 缺陷 3：脚本引用页内不存在的对象 —— 6 处（这才是「索引超出数组界限」的直接触发）

**成因**：厂家页克隆了主页时间镜像 `rY_f/rM_f/…`，并在页 `load` 事件里写

```tjc
tm0.en=1
```

但**没克隆主页的 `tm0`（定时器）**。编辑器按名字查本页对象表 → 找不到 → **索引超出数组界限**。

**连带问题**：补克隆 `tm0` 后，它的脚本仍指向主页对象名
（`rY.val=rtc0` …），在厂家页里又变成 6 个新悬空引用。
必须同步改名为 `rY_f.val=rtc0` … `rsec_f.val=rtc5`。

**修复**：`clone_into_page.js` 克隆时按 renameMap 同步改写脚本对象名。

## 二、页块真实布局（纠错两次）

```
[0, 56)          头部（+4 size / +8 hdr=56 / +12 nobj / +24 name[16]）
[56, 56+12n)     对象表，每项 12B = {off, len, 0}
[56+12n, size)   对象体，连续无空隙
```

**表项 `off` 相对「块首+56」**，故首个对象 `off` 恒为 `12n`。

验证：`2.pa` 空页 `nobj=1` → `off=12`，实际对象起始于 68 = 56+12 ✓

★ **我曾两次怀疑 `lib/page.js` 的 `hdr + t.off` 写错了，两次都是错的 —— 它正确。**
教训：怀疑工具库之前，先在已知良好的 v8 上跑一遍自证。

★ 我还一度误判「页块尾部有属性名字典/字符串池」，那是**我自己累积 off 时起点取错**造出的假象
（把对象表当成了池）。教训：算偏移前先用一个已知良好的页做等式验证，
不要凭「字节长得像字符串」就下结论。

## 三、`codesXX-N` 里 N 的含义

- v8 全工程 **622 个事件**实测（排除 keybdB 的 577 个）：**N == 脚本行数，无一例外**
- 带 `if`/`{}` 的脚本**也按行数计**（`cf` 12 行声明 12、`sD` 6 行声明 6），**块不额外计数**
- keybdB 页（`1.pa`）28 个事件 + 主页 `ptg` 是历史遗留偏差，不计为问题

★ 我中途试过「N = 行数 + 块数」假设，被 `cf` 反例证伪（12 行声明 12 却含 2 个 `if`）。
**不要靠单样本拟合规则** —— 要用全量数据 + 反例交叉验证。

## 四、流程错误：三种修复必须【串行】

三个修复器最初各自以 HMI 为输入、各自输出**完整页块**，最后靠 `cp` 合并目录 ——
**后者覆盖前者，前面的修复全丢**（`v9_fixed3` 体检仍报 3 处 end + 1 处 att）。

修正：`fix_all.js` 对**同一个页块对象**依次施加三种修复，最后只 `build` 一次。

★ 更普适的教训：多个修复器 → 必须有单一入口串行编排，
或让每步的输入是上一步的输出。`cp` 合并不是安全的组合方式。

## 七、给后续改屏的硬规则

1. **改任何对象的脚本前，先确认它的 `att-NN` 首行和 `end` 末行位置** —— 这两个是结构骨架，不能动
2. **不要用 `filter(it => it.kind !== 'mark')` 清脚本** —— 会连带清掉 `att-NN`
3. **脚本行强制 <16 字节** —— `lib/page.js` 的 `L>=16` 启发式会把长行误判成 attr
4. **克隆对象进新页后，必须扫描该对象脚本里的每个对象名** —— 指向源页对象的引用全都要改名
5. **改完必须跑 `audit_hmi.js` 并与 v8 基线对比** —— 不是「跑通」，是「与基线一致」
6. **多处修复必须串行**，不要多个脚本各出一份完整页块再合并
