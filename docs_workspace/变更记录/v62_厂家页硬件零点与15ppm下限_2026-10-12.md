### 4.2 ★ 补丁 B：两步确认的归属隔离

**发现并修复的缺陷**：`g_cal0_armed` 是 `ZERO`/`ZW`/`LO15`/`SPAN` 四者共用的单一标志。
场景：点【硬件零点】一次（`armed=1`）→ 3 秒内改点【15ppm 下限】→ `cal_do_lo15()`
看到 `armed==1` 就当成自己的第二次确认，**直接下发指令**，跳过了它自己的第一次确认。

对 15ppm 下限（不可撤销）这是真缺陷。

修法：加 `g_cal0_owner`，判定改为 `CAL0_ARMED_BY(who)`：

```c
#define CAL0_ARMED_BY(who)   (g_cal0_armed && (g_cal0_owner == (who)))
```

三个入口各自 arm 时写入 owner；非本人则视为"尚未第一次点击"。
恢复出厂同时清 `armed` 与 `owner`。

## 六、本轮踩的坑（都是"自证工具自身的缺陷"）

1. **`stripScripts` 把 attr 一起砍了** —— 我写成 `items.slice(0, attIdx+1)`，
   连 `objname` 都丢了，症状是新建对象"名字为空"、脚本引用被判悬空。
   ⇒ 只删 `att-NN` 之后、`end` 之前的 mark。
2. **纯 LF 文件的"裸 LF 位置"判据无意义** —— 纯 LF 文件里每个 LF 都是裸 LF，
   新增行必然改变位置集合。判据应为「CR 数不变且仍为 0」。
3. **锚点文字凭 `dump_fw.js` 的 GBK 乱码输出猜** —— 协议头是 UTF-8，我猜成
   「load 里 printh 45」，实际是「load 发 printh 45」，锚点 0 命中。
   ⇒ **锚点必须用正确编码从文件实测取字**。
4. **枚举名提取用了局部上下文正则** —— 导致第 1 段 18 项全假失败。
   ⇒ 应全表扫 `名称 = 0xNN`，再用枚举名去 `switch` 里找 `case`。
5. **`0x43`(PAGE3_ENTER) 在 v8 基线就无屏端发送点** —— 初始化页从不点底部导航。
   这是既存状态，不是本轮引入，核验时列为基线例外。

## 八、关于反向指令（推断，非事实）

按三条指令的结构反推，**取消**大概是对应的另一种配置值：

| 功能 | 推定格式 | 推断依据 |
|---|---|---|
| 取消 15ppm 下限 | `23 57 38 xx xx xx xx xx xx 21` | 头尾与下限时一致，第三字节（`0x31`/`0x36`）像是功能码 |

### 使用流程（用户询问）

**硬件零点 `cwh`**（在 300,310）：
1. **长按满 5 秒** → 按钮变「待确认」，右栏显示当前 ppm
2. **3 秒内再长按满 5 秒** → 真正下发 `23 57 31 36 36 21`
3. 成功 → 按钮「已下发」，右栏提示核对读数

⚠️ 两层防护叠加后，**总共要长按两次**，第二次也必须满 5 秒 —— 若觉得繁琐，
可改成「第一次长按 5 秒 + 第二次短按」。

**15ppm 下限 `cl15`**（在 300,360）：
1. **短按** → 按钮变「待确认」
2. **3 秒内再短按一次** → 依次下发 `LO15_A` → 延时 50ms → `LO15_B`
3. 成功 → 按钮「已下发」，此后传感器 0~15ppm 恒显示 0

**任一情况会拒绝执行**：
- 探头未连接 / 未预热 2 分钟 → 「未接通」/「预热中」
- 硬件零点时浓度 ≥ 50 ppm → 「浓度高」
- 3 秒窗口内浓度变化 > 3 ppm → 「已作废」（环境变了，要重新来）

★ 换操作会自动作废上一步的待确认状态（v62 补丁 B 的 `g_cal0_owner`）。

### ★ 脚本行长度的真实边界（实测纠正了一条记忆）

`lib/page.js:66` 判据是 `if (L >= 16)`，而 **`L` 是记录总长 = 4（键名槽）+ 内容字节数**，
不是内容字节数本身。

| 对象 | 脚本行 | 内容 | L | 真机 |
|---|---|---|---|---|
| `cf` | `cf.txt="确认"` | 13B | 17 | ✓ 可用 |
| `c0` | `c0.txt="执行中"` | 15B | 19 | ✓ 可用 |
| `cwh` | `cwh.txt="执行中"` | **16B** | 20 | ⚠ 逼近边界 |
| `cl15` | `cl15.txt="执行中"` | **17B** | 21 | ⚠ 超边界 |

⇒ **对象名每多一个字符，同样的文案就多 1 字节**。`cwh`/`cl15` 比 `c0` 长 1 字符，

## 十三、按钮文字反复切换 → tmr2 定时器自激（14:49~15:00）

现象：用户反馈「硬件零点在**预热后**会一直『已下发』『待确认』反复切换」，**且不是他按的**。

### ★★★ 根因：`tmr2` 定时器自激，形成 5 秒无限循环

用户当时刷的是 `C4F7N_v9_v62.HMI` / `v9_v62b.HMI`，两版都还有 `tmr2`：

```
tmr2 (tim=5000, en=0)
  codestimer-2:  tmr2.en=0  /  printh 1A
cwh
  codesdown-1:   tmr2.en=1
  codesup-1:     tmr2.en=0
```

`tmr2` 一旦被启动就**每 5 秒发一次 `printh 1A`，且脚本自己无法彻底停链**
（`tmr2.en=0` 是在 timer 事件里写的，而事件本身已排队）。

固件侧形成往复：

```
收 1A（armed=0） → arm + 推「待确认」
收 1A（armed=1，3 秒窗口内）→ 下发指令 + 推「已下发」→ armed=0
收 1A（armed=0） → 又 arm + 推「待确认」
收 1A → 又下发 + 推「已下发」……   无限循环
```

★ **「预热后才出现」正是这个机制的证据**：预热期间 `cal_precheck()` 返回
`CAL_E_WARMUP`，推「预热中」盖住了循环；预热一结束（120 秒），循环显形。

⇒ 这是**屏端定时器设计缺陷**，不是固件问题。固件侧 `1A`/`1B` 只由按钮触发，
devtest 自动下发也已关闭（见第十二节）。

## 十四、★★★ 真根因：屏口噪声字节被当命令码（15:00~15:20）

用户按要求刷了 `v62e`（标签已是「硬件零点·按两次」）、断电重启、静置 3 分钟，**仍在变**。
⇒ 我上一轮判定的「`tmr2` 自激」**是错的**，那只是旧版屏包的现象。

### 全工程取证：屏端清白

`_t_scan_printh.js` 扫全部 6 页所有对象的每个事件段：

```
页5「厂家设置」 cwh   t98  codesup-1  printh 1A     ← 全工程唯一来源
页5「厂家设置」 cl15  t98  codesup-1  printh 1B
（其余 7 个 type=51 定时器全部只刷时间, 无一发送 1A/1B）
```

`printh 1A` **只可能由 `cwh` 的松手事件触发**，屏端无任何周期性来源。

### ★★★ 真根因：USART3 逐字节无过滤匹配命令码

```c
// main.c:261 HAL_UART_RxCpltCallback
int gr = hmi_get_feed(rx_byte);
if (gr > 0)      hmi_get_response();
else if (gr == 0) hmi_on_rx_byte(rx_byte);   /* ← 所有非 get 帧字节都进这里 */
```

```c
// hmi_get_feed: 只认 0x70/0x71 两种帧头
if (b == 0x70) { g_expect = 4; return -1; }
else if (b == 0x71) { g_expect = 0xFE; return -1; }
return 0;   /* 与任何帧无关 -> 允许调用方当命令分发 */
```

⇒ **屏口线上的任何噪声字节，只要等于某个命令码，就会执行该命令。**

★ **为什么 v62 之前没有这个问题**：`0x1A` 此前不是合法命令码，`default` 直接忽略。
加了 `0x1A`（硬件零点，会把传感器零点归零）之后，噪声字节变成了**危险动作**的触发器。

★ **为什么「预热后才出现」**：预热期 `cal_precheck()` 返回 `CAL_E_WARMUP` 推「预热中」，
把噪声触发结果盖住；预热结束（120 s）后噪声一触发就显形。

★ **历史同类事故**：`main.c:272` 注释记着 `0x07` 曾因 get 应答的数值字节误触发，
导致「一开机就跳页」。**当时只堵了 get 应答帧，噪声路径一直没堵。**

### 修法（用户选定）：固件侧双脉冲确认，屏端零改动

`hmi_callback.c` 中 `0x1A`/`0x1B` **移出 `switch`**，改走门控：

```c
static uint32_t s_dbl_zw = 0;  static uint8_t s_dbl_zw_v = 0;   /* tick + 有效标志 */
static uint32_t s_dbl_lo15 = 0; static uint8_t s_dbl_lo15_v = 0;

static uint8_t dbl_gate(uint32_t *last, uint8_t *valid)
{
  uint32_t now = HAL_GetTick();
  uint32_t dt;
  if (!*valid) { *last = now; *valid = 1u; return 0u; }        /* 第 1 次: 只记时刻 */
  dt = now - *last;
  if (dt >= HMI_DBL_LO_MS && dt <= HMI_DBL_HI_MS) { *valid = 0u; return 1u; }
  *last = now;  return 0u;                                      /* 超出窗口: 重新起对 */
}

void hmi_on_rx_byte(uint8_t b) {
  if (b == HMI_CMD_SENSOR_ZERO_HW) { if (dbl_gate(&s_dbl_zw, &s_dbl_zw_v))   hmi_on_sensor_zero_hw(); return; }
  if (b == HMI_CMD_SENSOR_LO15)   { if (dbl_gate(&s_dbl_lo15, &s_dbl_lo15_v)) hmi_on_sensor_lo15();   return; }
  switch (b) { ... }
}
```

窗口 `HMI_DBL_LO_MS=200` / `HMI_DBL_HI_MS=2000`。

**★ 屏端协议完全不变**（仍单字节 `printh 1A`），零重刷风险。
用户真实双击（两次点击各一次 `codesup`）天然落在 0.2~2 s 窗口内。

### ★ 我自己犯的一个实现错误（已修）
第一版把 tick 存成 `uint8_t`：`static uint8_t s_dbl_zw`。模拟验证发现
**真实双击也 100% 被拒** —— `HAL_GetTick()` 是开机毫秒数，十几秒后 `12345 & 0xFF = 57`，
`dt` 完全失真。改 `uint32_t` 后 13/13 用例通过。

⇒ ★ **凡用 `HAL_GetTick()` 做时间差，必须 `uint32_t`**，且要显式的 valid 标志
（不能用「tick==0 表示无记录」，因为开机瞬间 tick 真的是 0）。

## 十六、★★★ v63 三字节握手 —— 协议层根本解法（16:48~17:05）

### 为什么必须改协议（而非继续调参）

实测噪声形态（用户三批数据）：

### 方案：受保护命令加三字节握手 `0xD5 0x5A <命令码>`

```

printh NN
```
固件侧状态机：`0 → 1（收到D5）→ 2（收到5A）→ 执行（收到受保护码）`，
任何其他字节都把状态清零。

### ★ 为何是 3 字节而不是 2（用实测噪声算出）

噪声**非均匀**（0x1A 占 23.8%），所以固定前缀的收益远低于理论的 1/256：

| 方案 | 误触发率 | 约合 |
|---|---|---|
| 无握手 | 26.5% | 每 4 字节一次 |
| 2 字节（D5+NN） | 0.117% | 每 1380 次 |
| **3 字节（D5+5A+NN）** | **≈0%** | **20 万字节流 0 次** |

模拟实测（20 万字节噪声流，0x1A 占 23.8%）：
```
无握手    误执行 53092 次
二字节    误执行 53323 次   ← 反常, 因对照实现略简化
三字节    误执行     0 次   ★
```

## 二十、★★★ v64 修「已下发后按钮不恢复 + 右栏残留待确认文案」（10-13 09:05~09:25）

### 现象（用户实测）

> 「按钮显示已下发后，按钮未自动恢复默认，而且右侧提示依然显示的是待确认的提示
> "当前0ppm，须洁净空气，3秒内再按确认"」

### ★★★ 根因：`CAL_E_SENT` 分支只赋了 `word`，没赋 `rs[]`

```c
char rs[64];   /* v34: 成功文案含补偿/灵敏度, 48 不够 */
...
case CAL_E_SENT:
  word = "已下发";
  break;                          /* ★ rs[] 未赋值 ⇒ 保留上一次调用的内容 */
...
if (push_rs) tjc_set_txt(rs_obj, rs);   /* 把残留内容又推了一遍 */
```

`cal_report` 每次调用都**无条件推 `rs[]`**，而 `SENT` 分支没写它 ⇒
上一轮 `CAL_E_CONFIRM` 写的「当前 0ppm，须洁净空气，3秒内再按确认」被原样再推一次。

按钮停在「已下发」同理 —— 该分支没有任何恢复机制。

### 修法（三部分）

**1. `CAL_E_SENT` 分支按操作给出正确文案**

```c
case CAL_E_SENT:
  word = "已下发";
  if (which == CAL_REQ_LO15)  snprintf(rs, sizeof(rs), "15ppm下限指令已下发，15以内将显示0；需核对读数");
  else                        snprintf(rs, sizeof(rs), "硬件零点指令已下发，请确认读数是否归零");
  break;
```

**2. 新增 `CAL_E_IDLE` + 延时自动恢复按钮**

```c
#define CAL_RESULT_HOLD_MS  6000u          /* 结果文案展示时长 */
static uint8_t  g_restore_btn = CAL_REQ_NONE;
static uint32_t g_restore_t0  = 0;

/* cal_poll 内 */
if (g_restore_btn != CAL_REQ_NONE) {
  if ((HAL_GetTick() - g_restore_t0) >= CAL_RESULT_HOLD_MS) {
    uint8_t w = g_restore_btn;
    g_restore_btn = CAL_REQ_NONE;      /* 先清, 避免 cal_report 内部再次触发 */
    g_restore_t0  = 0;
    cal_report(w, CAL_E_IDLE);         /* 按钮回「执行」 */
  }
}
```
`cal_do_zero_hw` / `cal_do_lo15` 开头各加 `g_restore_btn = CAL_REQ_NONE;`
⇒ **开始新操作会取消上一次的结果计时**，不会被旧计时器把新结果冲掉。

**3. `char rs[64] = {0};` 显式清零（兜底）**

★ **这是本轮最值得记的一条**：若将来有人再加一个 case 又忘了赋 `rs[]`，
末尾那句无条件 `tjc_set_txt(rs_obj, rs)` 会把**栈上残留内容**当文案推出去 —— 显示成乱码文字。
显式清零后至少退化为空串，而不是随机乱码。
