## 二、P1-A · 阈值按键被静默丢弃 —— 放弃判据从「重试次数」改为「耐心时间」

### 2.1 动手前先纠正我自己报告里的一处不准确表述

二次排查报告写的是「`g_get_busy` 互斥让阈值**连续让出 5 次**后 `g_thr_hi_req=0` 丢弃该次按键」。**这个机理描述错了。**

看 v55 的实际代码：

```c
static void thr_hi_readback_poll(void) {          /* v55 */
  if (!g_thr_hi_req) return;
  if (g_thr_wait) { if (now > g_thr_deadline) { g_thr_wait = 0; g_get_busy = 0; } else return; }
  if (g_rtc_wait) return;               /* ← 让出, 在下一行之前 */
  if (g_thr_try >= 5u) { g_thr_hi_req = 0; ... return; }   /* ← 放弃 */
  g_thr_try++;                                    /* ← 计数只在这里 +1 */
  g_thr_wait = 1; g_get_busy = 1; g_thr_deadline = now + 500u;
  tjc_get(OBJ_THR_HI_VAL, "val");
}
```

`if (g_rtc_wait) return;` 在 `g_thr_try++` **之前** ⇒ **让出通道根本不消耗重试预算**。
真正吃掉 5 次预算的是**每一次 `tjc_get()` 的 500 ms 应答窗口到期**（`g_thr_wait` 超时分支）。

### 2.2 真正的丢失条件

**500 ms 窗口 < 上电阶段屏重建页面的阻塞时长。**

- 上电后 `refill_table()` 一次全表重绘，固件侧阻塞约 1.8 s（v54 已实测）
- 此时若用户在设置页按阈值键盘，`tjc_get()` 的回包会被这段阻塞拖到 500 ms 之外
- 5 次重试全超时 → `g_thr_hi_req = 0` → **用户的按键被静默丢弃，无任何提示**

⇒ 时间窗恰好覆盖「上电后那几秒」，与实测现象吻合。

### 2.3 改法

新增按键时刻记录，放弃判据由「重试 5 次」改为「耐心 `THR_HI_PATIENCE_MS` 未获应答」：

```c
#define THR_HI_PATIENCE_MS 8000u   /* [v56] 阈值回读的等待上限(墙钟) */

static uint32_t g_thr_t0 = 0;      /* 用户按键时刻 */

void hmi_on_thr_hi_set(void) { g_thr_hi_req = 1; g_thr_try = 0; g_thr_t0 = HAL_GetTick(); }

/* thr_hi_readback_poll() 内 */
if ((uint32_t)(now - g_thr_t0) >= THR_HI_PATIENCE_MS) {
  g_thr_hi_req = 0; g_thr_try = 0; g_get_busy = 0; g_thr_wait = 0; return;
}
```

⇒ 屏幕慢不再被误判为「不响应」；只有连等 8 s 仍无应答才放弃（那才是真故障）。

**仍然必须清 `g_get_busy`** —— 这一条从 v51 起就没变，漏了会让 RTC 校时永久堵死。

### 2.4 残留风险（已核对，可自愈）

放弃边界上**迟到**的回包会被 `hmi_get_response()` 的 RTC 分支消费（此时 `g_get_busy` 已被清）。
但阈值量程 `100~1500` 与年份 `2020~2099` 不重叠 ⇒ 会被 `y >= 2020` 校验拒绝 ⇒ RTC 自动重试 ⇒ **自愈**。

### 2.5 附带订正注释

`if (g_rtc_wait) return;` 的注释原写「键盘回读有 5 次重试, 会重试到」—— 已改为「不消耗重试预算(让出在 `g_thr_try++` 之前)」，避免后人再误读成 2.1 节那个错误机理。

## 三、P1-B · 看门狗完全移出 ISR

### 3.1 原风险

`hmi_on_page_enter()` 处在 USART3 ISR 上下文，原先调 `iwdg_enable(); iwdg_feed();`。
而 `iwdg_feed()` **本身会裁决是否 `NVIC_SystemReset()`** ⇒
「**任何一次屏端切页事件都能触发复位**」：噪声误发 `0x40~0x43` + 主循环恰已卡住 > 4 s ⇒ 切页瞬间直接复位。

### 3.2 `iwdg_enable()` 一并移出的理由（比报告更彻底）

`iwdg_enable()` 会重置 `g_iwdg_t`，**等价于让 ISR 活动刷新软件狗的计时** ⇒ 会**掩盖**「主循环已停」这一本该触发复位的真状态。
所以它和 `iwdg_feed()` 是一类问题，报告里「只移 `iwdg_feed`、保留 `iwdg_enable`」的处置不够彻底，**两行一起移**。

### 3.3 移出后安全性不降反升

v53 已启用硬件 IWDG，由独立 LSI 驱动、**不依赖 CPU**：

| 场景 | 保护 |
|---|---|
| 主循环卡住 | 硬件狗在 **2.13~4.27 s** 内独立复位（不再依赖 ISR 刷新计时）|
| ISR 活动 | 不再能「掩盖」主循环已停 |

### 3.4 全工程喂狗点复核（移出后）

| 位置 | 上下文 |
|---|---|
| `main()` L454 `iwdg_enable()` + L455 `iwdg_feed()` | 上电初始化尾部（`iwdg_hw_start()` 之后）|
| `main()` L466 `iwdg_feed()` | 主循环 `while(1)` 顶部，每轮无条件 |
| `refill_table()` L890 | 行循环内每 2 行（v55 加密）|

⇒ **全部在主循环 / 初始化上下文，ISR 内零喂狗点。**

### 3.5 反汇编铁证

`hmi_on_page_enter`（`0x08005ac4`）函数体：

```
STRB r0,[r1,#0]      ; g_page_now = p
STRB r2,[r1,#1]      ; g_full_dirty = 1
STRB r1,[r0,#0xc]    ; g_cal_st_dirty = 1
STRH r2,[r1,#0xc]    ; g_thr_push = 1
STRB r1,[r0,#0]      ; g_tbl_page = 1
BX   lr
```

**零 `BL` 指令** —— 看门狗调用已被编译器彻底优化掉（若保留，函数体内必然出现 `BL iwdg_feed` / `BL HAL_IWDG_Refresh`）。

## 五、✅ 真机验证通过（2026-10-10）

用户实测确认：**开机按键跳过预热 → 更改报警阈值 → 立即生效 → 切屏与重启后数据均保持更改后的值**。

| # | 场景 | 期望 | 结果 |
|---|---|---|---|
| **1** | **开机按跳过预热，随后立即改高报阈值** | **阈值立即生效**（P1-A 决定性检验；v55 及以前在此窗口内可能被静默丢弃）| ✅ |
| **2** | 改阈值后**切屏** | 新值保持 | ✅ |
| **3** | 改阈值后**重启** | 新值保持（已落盘，非仅内存）| ✅ |

⇒ **P1-A 确认修复**：跳过预热后正是「校时窗口 + 页面重建」叠加的最恶劣时刻，此时按键仍能被正确采纳，说明墙钟 `THR_HI_PATIENCE_MS` 判据替代重试次数判据有效。
⇒ 同时验证了 `thr_apply_hi_val()` → `thr_commit()` → `param_save_safe()` 整条落盘链未受影响（**重启后值仍在** = 真落盘，不是 RAM 缓存）。
⇒ **P1-B 无回归**：切屏与重启均正常，未出现意外复位（若 ISR 喂狗残留，切页噪声 + 主循环卡住的组合会触发复位）。

**未覆盖项**（本次未涉及，供后续需要时再测）：长时静置 10 分钟的看门狗长跑回归、历史时间戳与屏端 RTC 一致性。
