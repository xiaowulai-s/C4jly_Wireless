## 一、起因：用户反馈「历史页 5 秒更新一次、一次更新五条」

用户观察准确，这正是 v54 降频的直接后果。

### 为什么会这样

`refill_table()` **一次仍然是全表重填 24 行**（每行 时间/浓度/序号 3 条，共 78 条消息）。
v54 改的是**触发间隔**，不是"一次填多少"：

| |触发条件 | 用户观感 |
|---|---|---|
| v53 及之前 | 记录条数变化即刷新（测试中每秒 1 条 ⇒ 每秒触发）| **每秒更新、每次 1 条** |
| v54 | 测试中加 `!g_test` 限制 ⇒ 只靠 5 s 兜底 | **每 5 s 更新、一次跳出 5 条**（5 s × 1 条/s = 5 条）|
| **v55** | 恢复「条数变化即刷新」| **回到每秒更新、每次 1 条** |

---

## 二、v54 的降频措施其实是**多余的**

v54 当时做了三处加固，事后看**降频是唯一有观感代价的一条**：

| 防线 | v54 做法 | 是否必需 |
|---|---|---|
| (a) `refill_table` 循环内喂狗 | 每 6 行喂一次 | ✅ **真正兜底**——单次调用不会累计到超窗口 |
| (b) `tjc_send_raw` 超时 100→20 ms | 异常时 78×20 = 1560 ms | ✅ **真正兜底**——落在 2133 ms 窗口内 |
| (c) 测试中降频到 5 s | 消除每秒触发 | ❌ **多余**——(a)(b) 已足够，(c) 只是额外压制，代价是牺牲实时性 |

⇒ v55 撤销 (c)，保留并**加固** (a)。

## 三、改动（1 文件，2 处逻辑）

### 改动 1· 恢复「条数变化即刷新」（去掉 `!g_test`）

```c
else if (g_page_now == 2u && (tot != s_total || g_tbl_page != s_pg)) { ... refill_table(); }
```

### 改动 2 · 喂狗密度由「每 6 行」加密到「每 2 行」

```c
if ((i % 2u) == 0u) iwdg_feed();     /* 原 % 6u */
```

**为什么加密**：恢复每秒刷新后，单轮最坏耗时需重新核算——

| 场景 | 单轮耗时 |
|---|---|
| `refill_table` 正常 | ≈ 186 ms |
| `refill_table` 异常（每次等满 20 ms）| 24 × 3 × 20 = **1440 ms** |
| 加 `history_log` 扇区擦除（仅新扇区首点）| 1440 + 500 = **1940 ms** |
| **IWDG 窗口（最快 LSI 60 kHz）** | **2133 ms** |

⇒ 1940 ms 只剩 **193 ms 余量（9%）**，太窄。

**加密后每 2 行的最坏耗时 = 2 × 3 × 20 = 120 ms** ⇒ 任何局部卡顿都无法累计到超窗口。
这是恢复「每秒刷新」的安全前提。
