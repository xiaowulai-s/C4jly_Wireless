## 1. 背景与目标

### 1.1 背景

现有便携式 C4F7N 检漏仪（STM32F103RCT6 主控 + GC5G1 NDIR 传感器 + W25Q64 存储 + TJC 7 寸串口屏）已完成 V1.0-b98 基线收口，整机真机验证通过。现启动**无线版**产品线：

- 抛弃 TJC 串口屏，设备端改为"小 OLED + 实体按键"的极简本地交互；
- 手机 App 通过 **BLE 近场直连**承担全部人机交互；
- **USB 数据线连电脑**，电脑端软件承担数据导出与厂家级维护。

### 1.2 产品目标

| # | 目标 | 验收口径 |
|---|---|---|
| G1 | 手机 App（用户端/厂家端）通过 BLE 完成测量显示、曲线、历史、设置、校准全部操作 | 真机闭环 + 真机验证清单全过 |
| G2 | 设备本地保留 OLED（浓度+电量）+ 实体按键（开泵、静音）的最小交互 | 断开 App 后设备可独立完成测量与报警 |
| G3 | 电脑端（用户端/厂家端）通过 USB 数据线导出数据、执行厂家操作 | PC ↔ 设备真机联调通过 |
| G4 | 新增能力：检测任务归档、检测报告导出（PDF/Excel）、多设备管理、报警事件记录、标定向导、BLE OTA | 逐项功能验收 |
| G5 | 暂不上云，但硬件与协议预留上云升级空间 | 架构评审确认（传输层可替换） |
| G6 | 1~2 周出第一个可验证里程碑（MVP：真机 BLE 闭环） | 里程碑 M1 |

### 1.3 产品形态定义

| 软件 | 使用者 | 承载平台 | 交付形态 |
|---|---|---|---|
| 用户端 App | 客户 | Android | APK 直接分发（不上市应用商店） |
| 厂家端 App | 本公司售后 | Android | APK 仅内部持有 |
| 用户端 PC 软件 | 客户 | Windows | 安装包（Tauri 打包） |
| 厂家端 PC 软件 | 本公司售后 | Windows | 安装包仅内部 |

## 2. 总体架构

### 2.1 系统拓扑

```
┌────────────────────────────── 设备端（外挂验证阶段）──────────────────────────────┐
│                                                                                  │
│   GC5G1 传感器 ──UART──┐                                                          │
│   W25Q64 存储 ──SPI────┤   ┌──────────────────┐      UART1(115200)  ┌─────────┐  │
│   电池 ADC(分压) ──────┼───┤  STM32F103RCT6   │◄──────────────────►│ESP32-S3 │  │
│   泵/蜂鸣器/LED ──GPIO─┤   │ 现有业务固件      │   协议v1 帧流       │ BLE     │  │
│   按键(泵/静音) ──GPIO─┤   │ + wireless.c     │                    └────┬────┘  │
│   OLED ──SPI/I2C───────┘   └──────────────────┘                         │ BLE 5  │
│                                                                          ▼        │
│                                                             Android 手机 App      │
│                                                          （用户端 / 厂家端）       │
└──────────────────────────────────────────────────────────────────────────────────┘
                                       │
                        USB 数据线（ESP32-S3 原生 USB-OTG / USB-CDC）
                                       ▼
                        Windows 电脑软件（Tauri 2 + React 19 + Rust）
                                （用户端 / 厂家端）
```

### 2.2 分层原则（本项目最重要的架构决策）

| 层 | 所在硬件 | 职责 | **明确不做的事** |
|---|---|---|---|
| **业务层** | STM32 | 测量、标定、参数、历史、报警、自检——全部业务逻辑 | 不感知 BLE 存在 |
| **协议层** | STM32（`wireless.c`） | 协议 v1 帧编解码、CRC、命令分发、会话令牌校验 | 不做业务决策 |
| **传输层** | ESP32-S3 | BLE GATT ↔ UART 透明桥接、链路管理（广播/连接/MTU/心跳转发） | **不解析、不缓存、不修改业务帧** |
| **应用层** | App / PC | UI、任务归档（SQLite）、报告生成、权限分级、扫描连接 | 不做测量/标定计算 |

**为什么这样分**：传输层做薄，将来上云（4G/WiFi 模块替换 ESP32）或换传输方式（USB 直连、UART 调试）时，STM32 业务固件与协议 v1 **零改动**；App 与 PC 共用同一套协议编解码逻辑，两端行为一致。

### 2.3 关键数据流

```
[实时数据] GC5G1 → sensor.c 解析 → 测量管线 → wireless.c 打包(0x10, 1Hz)
          → USART1 → ESP32 → BLE Notify → App 曲线/大数字

[控制命令] App → BLE Write → ESP32 → USART1 → wireless.c 解析校验
          → 分发到 pump/param/calib 现有 handler → ACK 帧原路返回

[历史回放] App → 0x40 分页读 → wireless.c → history.c → W25Q64 → 分帧回传
```

## 3. 硬件方案

### 3.1 BLE 主控选型：**ESP32-S3（首选定稿）**

| 对比项 | ESP32-S3（✅ 首选） | ESP32-C3（备选） |
|---|---|---|
| CPU | 双核 Xtensa LX7 @240MHz | 单核 RISC-V @160MHz |
| RAM | 512KB（可加 PSRAM） | 400KB |
| BLE | 5.0（NimBLE 支持）✅ | 5.0（NimBLE 支持）✅ |
| USB | **原生 USB-OTG（USB-CDC）** ✅ | 仅 USB-Serial-JTAG |
| GPIO | 多（45） | 少（22） |
| 单价 | 略高（约贵几元） | 低 |
| 本项目结论 | **定稿采用**：双核跑 BLE+UART 更稳；USB-OTG 让电脑端直连免外挂 CH340；RAM 余量支撑将来上云 | 功能上完全够用，作为缺货时的等价替代（仅改引脚映射） |

> 本项目透传网桥对算力要求极低，S3 属于"性能过剩"，换取的是**双核稳定性、USB 直连、未来上云余量**三重保险。

### 3.2 外挂验证阶段接线（不改现有 PCB）

| 信号 | STM32 侧 | ESP32-S3 侧 | 说明 |
|---|---|---|---|
| TX | PB6（USART1_TX） | RX（UART0 RX，经电平确认） | 115200-8N1 |
| RX | PB7（USART1_RX） | TX | 115200-8N1 |
| GND | GND | GND | **必须共地** |
| 供电 | — | 5V → 板载 LDO → 3.3V | ⚠️ ESP32-S3 Wi-Fi 发射峰值电流可达 ~500mA，验证阶段只用 BLE 峰值较低，但务必从整机 5V 取电，勿接 3.3V 轨直接拖载 |
| 电平确认 | — | — | ⚠️ 动手前实测 USART1（PB6/PB7）当前是否确实空闲、3.3V 电平匹配（风险 R4） |

### 3.3 本地显示与按键（新板阶段实装，验证阶段可先不接）

| 部件 | 选型 | 接口 | 显示内容 |
|---|---|---|---|
| OLED | 1.14" ST7789（SPI，首选，更大更清晰）或 0.96" SSD1306（I2C，备选） | SPI1 / I2C 空闲口 | 浓度大数字（ppm）、电量条、BLE 连接图标、报警红字 |
| 按键 | 2 个（开泵、静音），GPIO + EXTI，复用现有去抖逻辑 | — | 长按/短按语义 Phase 3 定稿 |

### 3.4 电池与功耗

- 整机电池体系（14.8V 锂电）不变，ESP32-S3 取电接现有 5V 轨；
- BLE 连接参数（间隔 30~50ms）下 ESP32-S3 平均电流约 30~50mA，对整机续航影响 <5%（现有泵功耗远大于此）；
- 设备可配置"BLE 常广播"或"按键唤醒广播"两种策略，默认常广播（验证阶段简化）。

## 4. 无线通信协议 v1（详细规范）

> ⚠️ 本章为**三方契约**（App / ESP32 / STM32）。评审通过后冻结版本号 `WL-PROTO-1.0`，此后任何变更必须走变更记录并同步三方。

### 4.1 帧格式

```
偏移   0      1      2      3      4 .. 3+N      4+N     5+N
     +------+------+------+------+-------------+--------+--------+
     | 0xA5 | 0x5A | LEN  | CMD  |   PAYLOAD   | CRC_L  | CRC_H  |
     +------+------+------+------+-------------+--------+--------+
```

| 字段 | 长度 | 说明 |
|---|---|---|
| 帧头 | 2 B | 固定 `A5 5A`（已避开现有 TJC 帧与 GC5G1 传感器帧特征） |
| LEN | 1 B | CMD + PAYLOAD 的字节数（不含帧头与 CRC），**≤ 240** |
| CMD | 1 B | 命令字，见 §4.3 |
| PAYLOAD | 0~239 B | 字段小端序（little-endian），多字节整数低字节在前 |
| CRC | 2 B | CRC16-MODBUS（多项式 0x8005，初值 0xFFFF，低字节在前），计算范围 = CMD + PAYLOAD |

- 字符串字段一律 **GBK**（与设备端现有字符串编码一致，App 端负责转换）；
- 浮点字段用 IEEE754 单精度（4 B，小端）；
- 保留字段必须填 0。

### 4.2 传输与时序规则

| 规则 | 值 |
|---|---|
| BLE MTU | 连接后协商至 **247**；单帧 ≤240 B 保证一个 MTU 装下，BLE 层不再分片 |
| 写特征方式 | Write Without Response（靠 CRC + ACK 保证可靠性） |
| 命令应答 | 每条 App→设备命令，设备必须回 ACK/NACK（同 CMD 字段的响应帧），超时 **2 s** 判失败，App 重试 1 次 |
| 心跳 | App 每 5 s 发 0x01；设备 **15 s** 未收到任何帧 → 判 App 离线（仅影响 BLE 图标与远程静音恢复） |
| 掉线重连 | ESP32 端连接断开后自动恢复广播；App 扫到即连（自动重连策略在 App 端实现，指数退避） |
| 并发 | 同一时刻只允许一条未应答命令（请求-响应锁），设备端 FIFO 深度 4 |

### 4.3 命令集总表

| CMD | 名称 | 方向 | 权限 | 说明 |
|---|---|---|---|---|
| 0x01 | 心跳/握手 | 双向 | 通用 | 见 §4.4 |
| 0x10 | 实时数据上报 | 设备→App | 通用 | 1 Hz 主动 Notify |
| 0x11 | 参数读 | App→设备 | 通用 | 单参数 ID 读取 |
| 0x12 | 参数写 | App→设备 | 通用* | 写后 ACK 携带回读值 |
| 0x20 | 泵控制 | App→设备 | 通用 | 开/关 |
| 0x21 | 静音控制 | App→设备 | 通用 | 报警静音；App 离线后设备自动解除静音（恢复本地报警） |
| 0x30 | 零点校准 | App→设备 | 通用 | 两步确认流程 |
| 0x31 | 厂家标定/补偿 | App→设备 | **厂家令牌** | 斜率/截距、手动 b/k（20% 变更二次确认） |
| 0x40 | 历史数据读 | App→设备 | 通用 | 按扇区分页读取 |
| 0x41 | 历史删除 | App→设备 | 通用* | 二次确认 |
| 0x50 | 自检 | App→设备 | 通用 | 泵/存储/传感器诊断 |
| 0x60 | 事件上报 | 设备→App | — | 设备主动推送 |
| 0x70~0x7F | OTA 命令族 | 双向 | **厂家令牌** | Phase 4 实装，协议字段预留 |

**权限说明**：标 `*` 的命令（阈值写、历史删除）App 端强制二次确认；标"厂家令牌"的命令，设备端校验会话令牌（§4.5），无令牌回 NACK(0x03)。

### 4.4 各命令 payload 字段定义

> 全部字段小端序；`u8/u16/u32` = 无符号整数，`f32` = 单精度浮点，`char[n]` = GBK 定长字符串。

**0x01 心跳/握手**

```
App→设备（4 B）：
  u32 proto_ver      // 协议版本，固定 0x00000100（v1.0）
设备→App（12 B）：
  u32 proto_ver      // 设备侧协议版本
  u8  battery        // 电量百分比 0~100
  u8  device_state   // bit0 泵运行 bit1 报警中 bit2 静音 bit3 历史满告警
  u8  fw_major, fw_minor   // 固件版本号（对应 PRODUCT_FW_VERSION）
  u8  rssi_adj       // 保留，填 0
  u8  reserved[4]    // 保留填 0
```

**0x10 实时数据上报（设备→App，1 Hz）**

```
（16 B）
  u16 conc_x10       // 浓度 ppm×10（如 12.4ppm → 124）
  u16 temp_x10       // 传感器温度 ℃×10（GC5G1 提供）
  u16 peak_x10       // 本次开机以来峰值 ppm×10
  u8  battery        // 电量 %
  u8  device_state   // 同 0x01 定义
  u16 alarm_th_x10   // 当前报警阈值 ppm×10（省一次参数读）
  u32 uptime_s       // 开机秒数
```

**0x11/0x12 参数读/写**

```
0x11 App→设备（2 B）：  u16 param_id
0x11 设备→App（2+4 B）：u16 param_id + u32 raw_value（含义由 param_id 决定）
0x12 App→设备（2+4 B）：u16 param_id + u32 raw_value
0x12 设备→App（2+4 B）：同上（ACK 回读值，写入失败回 NACK）
param_id 表（对齐 param_store 现有字段）：
  0x0001 报警阈值（ppm×10）
  0x0002 采样周期（s）
  0x0003 手动补偿 b（f32）
  0x0004 手动补偿 k（f32）
  0x0005 泵自动启动开关（u8）
  0x0006 设备编号（u16，广播名用）
  …（Phase 0 冻结时对 param_store 全字段逐项编号，表放独立小节）
```

**0x20 泵控制**：`u8 on_off`（1=开 0=关）→ ACK（回显当前态）。
**0x21 静音**：`u8 mute_on_off`（1=静音 0=恢复）→ ACK。

**0x30 零点校准（两步，对齐现有屏版逻辑）**

```
App→设备（1 B）：u8 step    // 1=准备（设备回当前读数与稳定性） 2=确认执行
step=1 响应（8 B）：u16 conc_x10 + u16 stable_flag + u32 reserved
step=2 响应：ACK（成功）/ NACK（失败原因：1=读数不稳 2=传感器异常）
```

**0x31 厂家标定/补偿（需厂家令牌）**

```
App→设备（5 B）：u8 op + u32 raw_value
  op: 0x01 斜率标定  0x02 截距标定  0x03 写补偿 b(f32)  0x04 写补偿 k(f32)
  0x05 恢复出厂参数
k/b 变更幅度 >20% 时设备回特殊 ACK（0x81 需二次确认），App 必须再发一次 0x31 带
u8 confirm=1 才生效（对齐屏版 v79~v92 逻辑：按"值有没有变"判定，无时间窗口）。
```

**0x40 历史数据读**

```
App→设备（6 B）：u16 block_index + u16 count + u16 reserved
设备→App：多帧响应（每帧 u16 seq + 历史记录结构体，与 history.c 现有记录格式对齐，
Phase 0 冻结时把单条记录字段表抄录进协议文档；末帧 seq 高位置 1 表示结束）
```

**0x41 历史删除**：`u8 confirm`（0xAA=确认）→ ACK。
**0x50 自检**：无 payload → 设备→App（8 B）：各子项结果位图 + 每项 1 字节错误码。
**0x60 事件上报（设备→App 主动）**

```
（8 B）
  u8  event_id   // 1=报警开始 2=报警结束 3=低电 4=BLE恢复 5=历史满 6=泵异常
  u8  reserved[3]
  u32 timestamp_s  // 设备 RTC 时间戳
```

**0x70~0x7F OTA（Phase 4 实装，此处预留命名空间，协议冻结时占位不定义细节）**

### 4.5 会话令牌（厂家权限机制）

1. 厂家端 App/PC 在握手后发送 `0x7A 认证` 命令（预留位）：payload = SHA-256(厂家口令 + 设备 SN) 摘要前 16 字节；
2. 设备端预存相同算法的期望值（出厂烧写），比对通过后置位会话标志；
3. 会话标志随 BLE 断开 / 15s 无心跳自动失效；
4. 失败连续 5 次 → 锁定 10 分钟（防暴力尝试）；
5. 用户端 App **不包含**该口令，物理上无法通过 0x31/0x7A 校验。

### 4.6 BLE GATT 定义

| 项 | 值 |
|---|---|
| Service UUID | `A5F7N000-0000-1000-8000-00805F9B34FB` 风格自定义 128-bit（正式值 Phase 0 冻结时用随机生成器定稿并登记） |
| 特征 1（App→设备） | Write Without Response，UUID `...0001` |
| 特征 2（设备→App） | Notify，UUID `...0002` |
| 广播名 | `C4F7N-XXXX`（XXXX = 设备编号 u16 的十六进制，来自 param 0x0006） |
| 广播间隔 | 100~200 ms（快速被发现） |
| 连接参数请求 | 间隔 30~50 ms，slave latency 0，timeout 2 s |
| 安全 | 不做配对绑定（近场仪器场景，简化连接体验），靠会话令牌做权限 |
| 多设备 | 一台手机同时只连一台（场景决定），扫描列表支持任意多台展示与切换 |

## 5. STM32 固件设计

### 5.1 工程策略

- **从 `C4F7N_Demo`（V1.0-b98）复制分叉出独立工程 `C4F7N_Wireless/fw/`**，屏版工程 `C4F7N_Demo` 就此冻结（只收致命 bug，不加功能）；
- 编译工具链不变：AC6 (ARMCLANG 6.24)，`UV4 -j0 -b`；受限于本机 UV4 执行限制，日常改动用 `node _ac_check.js` 做 armclang 单文件校验，出 hex 才走 Keil。

### 5.2 模块改动清单

| 模块 | 动作 | 说明 |
|---|---|---|
| `Middleware/Src/wireless.c|h` | **新增** | 协议 v1 帧编解码、CRC16-MODBUS、命令分发、会话令牌状态机、1Hz 上报定时 |
| `BSP/Src/oled_st7789.c|h` | **新增**（Phase 3 实装） | 浓度+电量+报警图标最小显示，不做菜单 |
| `Core/Src/usart.c` | 修改 | USART1 使能 + 中断/DMA 收发（当前仅预留） |
| `Core/Src/main.c` | 修改 | 主循环挂 wireless 轮询（替代原 tjc 轮询位置） |
| `Middleware/tjc_cmd` / `hmi_callback` / `hmi_get` | **暂留不编译**，Phase 3 清理 | 保留参考价值（协议语义对齐） |
| `BSP/pump` / `selftest` / `param_store` / `history` / `battery` | **不动** | 业务 handler 原样复用 |

### 5.3 wireless.c 内部设计

```
状态机：IDLE → (收到0xA5) HEAD1 → HEAD2 → LEN → CMD → PAYLOAD → CRC → DISPATCH
接收：USART1 中断逐字节 + 环形缓冲（512B）
发送：帧组装 → USART1 TX（阻塞式即可，240B@115200 ≈ 21ms）
分发：cmd 表驱动（函数指针数组），handler 直接调用现有业务模块
会话令牌：单 bit 状态 + 失败计数器 + 锁定时间戳
1Hz 上报：复用现有测量节拍（RTC 秒 tick）触发打包
```

### 5.4 编码纪律（不可违反，源自 AGENTS.md 教训）

- **新 C 文件注释一律 ASCII**，杜绝 GBK/UTF-8 编码纠缠；
- 如确需中文注释：先判定目标文件真实编码，UTF-8 临时文件 → GBK 写出，PS 5.1 必须用 `[System.Text.Encoding]::GetEncoding(936)`；
- 每次改动后先 `node _ac_check.js <改动文件>` 校验，**禁止让用户直接 Rebuild 当验证**。

## 6. ESP32-S3 固件设计

### 6.1 技术选型

- **ESP-IDF（v5.x）+ NimBLE**：BLE 5 栈成熟、内存占用小、乐鑫官方长期维护；
- 语言 C（与团队嵌入式技能一致），规模预计 400~600 行。

### 6.2 模块结构

```
esp32/
├── main/
│   ├── main.c          // 初始化：NVS、NimBLE、UART、双核任务分配
│   ├── ble_gatt.c|h    // GATT Server：广播、连接管理、MTU 协商、Write/Notify 特征
│   ├── uart_bridge.c|h // UART 收发 + 帧定界（按 A5 5A+LEN 切帧，不解析内容）
│   └── link_mon.c|h    // 链路监控：连接断开自动恢复广播、UART 对端超时告警
```

### 6.3 核心行为

| 行为 | 规格 |
|---|---|
| 透传 | BLE Write 收到 N 字节 → 原样 UART TX；UART 收到完整帧 → BLE Notify。**零缓存零解析**（环形缓冲 1KB 防抖动） |
| 断线 | BLE 断开 → 200ms 内恢复广播；UART 静默 >20s → BLE 侧发链路告警帧（0x60 event_id=7） |
| 双核分工 | Core0：BLE 栈；Core1：UART 桥（ESP-IDF 默认布局基本即此） |
| USB-CDC | 同时使能 USB-CDC 作为第二条"UART"（与物理 UART 复用同一透传逻辑），供电脑端直连——**电脑端方案的关键前提** |

### 6.4 OTA 预留

- 分区表按标准 `factory + ota_0 + ota_1` 布局；
- Phase 4 的 OTA 目标有两个：**ESP32 自身 OTA**（走 BLE，标准 esp_ota 组件）与**STM32 固件 OTA**（ESP32 接收 → 透传给 STM32 的 bootloader，协议 0x70 命令族，Phase 4 细化）。

## 7. 手机 App 设计

### 7.1 技术栈（定稿）

| 项 | 选型 | 理由 |
|---|---|---|
| 框架 | **Flutter 3.x** | 一套代码出 user/factory 两 App；自绘引擎 UI 一致性最好；BLE/图表生态最优 |
| BLE | `flutter_blue_plus` | Android BLE 事实标准库，维护活跃 |
| 图表 | `fl_chart`（或自绘 CustomPainter） | 实时曲线流畅度足够（1Hz 数据） |
| 本地库 | `drift`（SQLite） | 类型安全，支持迁移 |
| 报告 | `pdf` + `printing`（PDF）、`excel`（Excel） | 纯 Dart 生成，无服务端依赖 |
| 状态管理 | `riverpod` | 数据源抽象与流式更新适配好 |

> 备选评估结论（已评审）：React Native（react-native-ble-plx）可行但 BLE/曲线生态略弱；uni-app 不推荐（Android BLE 坑多、依赖付费原生插件）；Kotlin 原生 BLE 控制力最强但两套 App 工作量×2，与 1~2 周 MVP 冲突。

### 7.2 工程结构（双 flavor）

```
app/
├── lib/
│   ├── core/
│   │   ├── protocol/        // 协议 v1 编解码（帧、CRC、命令，唯一事实源）
│   │   ├── ble/             // BleDataSource：扫描/连接/MTU/重连/心跳
│   │   └── mock/            // MockBleDataSource：开发期模拟数据源
│   ├── data/                // drift 表：task / alarm_event / device
│   ├── features/
│   │   ├── connect/         // 扫描、多设备管理
│   │   ├── measure/         // 测量主页
│   │   ├── task/            // 检测任务
│   │   ├── history/         // 设备历史回放
│   │   ├── events/          // 报警事件
│   │   ├── settings/        // 阈值、校准向导
│   │   ├── report/          // 报告导出
│   │   └── factory/         // 厂家端专属（flavor=factory 才编译）
│   └── main_user.dart / main_factory.dart
```

### 7.3 数据源抽象（支撑"先开发 App"）

```dart
abstract class DeviceDataSource {
  Stream<RealtimeFrame> realtime();          // 0x10
  Future<Ack> sendCommand(CmdFrame cmd);     // 请求-响应
  Stream<EventFrame> events();               // 0x60
  // ...按协议 v1 命令逐一定义
}
class BleDataSource implements DeviceDataSource { ... }   // 真机
class MockBleDataSource implements DeviceDataSource { ... } // 模拟
```

**BLE 外设模拟器 App（`sim/`，Phase 0 交付）**：独立小 App（Flutter 复用同一协议库），在任一 Android 手机上模拟检漏仪——按 §4.6 广播、推送 1Hz 假浓度（可配噪声/爬升曲线/报警场景）、响应泵/静音/校准/参数命令。**App 全部功能对着模拟器开发自测，ESP32 到货后切 `BleDataSource` 零改动。**

### 7.4 页面明细

**用户端（7 页）**

| 页面 | 功能要点 |
|---|---|
| ① 连接页 | 扫描 `C4F7N-*` 广播；设备卡片（名称/信号/电量）；多设备管理：重命名、收藏、最近连接排序；点卡片连接 |
| ② 测量主页 | 浓度大数字（ppm）、60s 实时曲线（1Hz）、峰值/阈值卡片、泵/静音快捷开关、连接与电量状态栏；报警时整页红色主题 + 震动 |
| ③ 检测任务 | 新建任务（站点名/间隔号/备注/检测时长）→ 检测中（曲线+实时值自动归档 SQLite）→ 结束生成任务摘要（峰值/超限次数/时长） |
| ④ 历史回放 | 0x40 分页读设备 Flash 历史，曲线缩放/平移，按时间段筛选 |
| ⑤ 报警事件 | 事件列表（时间/峰值/持续时长，来自 0x60 + 本地归档），点击跳对应任务 |
| ⑥ 设置 | 阈值修改（输入 → 二次确认 → 0x12）；零点校准**图形化向导**（步骤 1 准备读数稳定 → 步骤 2 确认 → 结果页，对应 0x30 两步协议） |
| ⑦ 报告导出 | 任务 → PDF（封面 + 曲线图 + 峰值表 + 操作人/时间）或 Excel；支持系统分享 |

**厂家端 = 用户端全部 + 以下 4 页（仅 factory flavor 编译）**

| 页面 | 功能要点 |
|---|---|
| ⑧ 厂家登录 | 口令输入 → 0x7A 认证 → 会话令牌；失败 5 次锁 10 分钟（与设备端同步） |
| ⑨ 标定 | 斜率/截距标定、手动补偿 b/k（0x31，>20% 变更触发设备端 0x81 二次确认，App 弹确认框，逻辑对齐屏版 v79~v92） |
| ⑩ 诊断 | 传感器原始帧透传显示、0x50 自检结果、参数全量读写（0x11/0x12 表格式）、恢复出厂（0x31 op=0x05） |
| ⑪ OTA | 固件包选择 → 0x70 命令族升级（Phase 4） |

### 7.5 本地数据模型（drift/SQLite）

```
device(id, name, sn, last_seen, is_favorite)
task(id, device_id, site, section_no, note, started_at, ended_at,
     peak_ppm, over_limit_count, curve_json)   // curve_json 只存关键采样点
alarm_event(id, device_id, task_id?, started_at, ended_at, peak_ppm)
```

**原则**：任务/事件存手机端为主；设备端 W25Q64 存储结构**不改**；任务曲线只存降采样关键点，完整历史需要时从设备实时读。

- 需申请：`BLUETOOTH_SCAN`、`BLUETOOTH_CONNECT`（API 31+）及旧版本 `ACCESS_FINE_LOCATION` 兼容路径；
- 交付前在测试手机（已备）上锁定验证；量产前扩充 3~5 款主流机型回归（风险 R2）。

## 8. 电脑端软件设计

### 8.1 技术栈（定稿）

### 8.2 架构

```
pc/
├── src-tauri/               // Rust 后端
│   ├── serial.rs            // serialport 打开 USB-CDC（ESP32-S3 原生 USB 口）
│   ├── protocol.rs          // 协议 v1 编解码（与 App 的 TS 版逻辑一致，互为参照）
```

- **连接路径**：电脑 USB ↔ ESP32-S3 USB-CDC ↔ （同一条透传逻辑）↔ UART ↔ STM32。**协议与 BLE 完全一致，硬件零新增**（替代原计划的 CH340 方案）；
- 协议编解码在 App 侧为 Dart、PC 侧为 Rust，两份实现互为交叉验证；如后续团队沉淀，可抽 WASM 共享（非必须）；
- 两个 flavor（`user` / `factory`，feature flag），页面职责同 §7.4 ⑧~⑪。

### 8.3 功能范围（Phase 4 交付）

用户端：历史数据导出（CSV/Excel）、曲线查看、阈值查看/修改、零点校准。
厂家端：+标定/b/k/自检/恢复出厂/STM32 OTA。

## 14. FAQ

**Q1：为什么 ESP32 不做业务逻辑？**
业务在 STM32 上已经真机验证过（标定、报警、历史），搬到 ESP32 等于重写并重新验证，风险巨大收益为零；ESP32 做薄，将来换传输方式（上云）STM32 零改动。

**Q2：为什么 BLE 不做配对绑定？**
仪器是单人近场操作场景，配对弹窗伤害连接体验；权限靠会话令牌控制，安全目标（防误操作厂家功能）已达成。

**Q3：App 断线后设备会失控吗？**
不会。报警逻辑设备自治（蜂鸣器/LED/OLED 本地执行）；App 静音是临时的，15 s 心跳超时设备自动恢复本地报警。

**Q4：为什么两套 App 用一个代码库？**
用户端与厂家端 90% 页面相同（用户端是子集），分库必然产生双份维护；flavor 编译隔离保证厂家功能不进用户端安装包。

**Q5：将来上云要改什么？**
仅替换传输层：ESP32-S3 加 WiFi/4G 模块连云服务，协议 v1 帧格式原样可走 TCP/MQTT；App 增加云数据源实现类；STM32 与业务层零改动。

**Q6：屏版还能用吗？**
能。`C4F7N_Demo` b98 + `C4F7N_v12.HMI` 冻结为屏版终版，功能完整可用；仅不再新增功能。
